# Системна архитектура и инфраструктура на LavBench

## 1. Общ преглед на системата

```text
Browser (React SPA) ──> Nginx (Port 80 / 443, HTTP(S) / SSE Reverse Proxy)
                            ├── Flask API Server (Port 5001, Gunicorn + gevent)
                            │     ├── PostgreSQL 15 (Primary Database)
                            │     ├── Redis (Celery Broker + Coordination: SSE pub/sub fan-out, worker_spec registry, submission fallback key, versioned leaderboard invalidations, dead-letter queue, GPU/build locks)
                            │     ├── Redis Cache (Private, server-only: leaderboard caches, locks, rate-limit counters, JWT blacklist — CACHE_REDIS_URL never given to external workers)
                            │     ├── Celery Beat (Periodic Scheduler: Backups, Watchdog)
                            │     ├── Internal Celery Worker (Short system tasks, inside Docker Compose, -Q celery,internal)
                            │     └── Long-job Celery Worker (Backups and nanoColab syncs, inside Docker Compose, -Q internal_long)
                            └── Remote Execution Workers (Celery evaluation-only workers: Docker container or host, consume cpu_queue, plus gpu_queue on GPU hosts)
                                  └── Sibling Sandbox Containers (--network none, --read-only, --cap-drop ALL)
```

## 2. Технологичен стек на компонентите

| Компонент | Технология | Роля и основни отговорности |
| :--- | :--- | :--- |
| **Клиентска част (Frontend)** | React 19 + Vite + Vanilla/Tailwind CSS | SPA с обновявания на живо чрез SSE, i18n (en/bg), JSDoc `@type` валидация (`tsc --noEmit`). |
| **API сървър** | Flask 3.1 + Gunicorn + gevent + spectree | REST API крайни точки, Pydantic v2 валидация на заявки/отговори, SSE поточно предаване на събития. |
| **Основна база данни** | PostgreSQL 15 | Потребители, състезания, етапи, задачи, решения, журнали за одит (`AuditLog`). |
| **Кеш и брокер** | Redis | Celery брокер на задачи + **клиент за координация** за цялото споделено състояние между машините: SSE pub/sub разпращане, регистър на спецификациите на работните възли (`worker_spec:<hostname>`), резервен ключ за решения, версионирани инвалидирания на класациите, опашка за необработени съобщения (dead-letter queue), заключвания за GPU и изграждане на образи, разпределени заключвания (за изпращане на решения и за класацията), броячи за ограничение на честотата, неуспешни опити за вход, отменени JWT токени и маркери за резервните копия. Устойчивостта чрез AOF и `noeviction` защитават задачите в опашката и тези гаранции. |
| **Самостоятелен кеш** | Redis (DB 1, `volatile-lru`, без устойчивост) | Частен сървърен кеш за данни, които могат да се изчислят наново: кешове за класацията и за състоянието, списъци за повторно възпроизвеждане на журналите по SSE и състояние на решенията (`CACHE_REDIS_URL`). Когато се напълни, изхвърля най-отдавна използваните ключове с TTL, затова нищо в него не бива да е необходимо за коректността. Вътрешен контейнер — без порт към хоста; външните работни възли никога не получават този URL. |
| **Опашка със задачи** | Celery 5.4 | Асинхронно изпълнение на фонови задачи (оценяване на решения, изграждане на образи, резервни копия на базата данни). |
| **Планировчик** | Celery Beat | Периодични задачи (контрольор за заседнали решения, график за автоматични резервни копия). |
| **Работни възли** | Celery работен възел за оценяване | Работни възли **само за оценяване**, които са консуматори на `cpu_queue`, а на хостове с GPU — и на `gpu_queue`; изпълняват кода на състезателя в съседни Docker контейнери с изолирана среда (`deploy-worker.sh` / `worker.env`). |

### Жизнен цикъл на миграциите на базата данни

В Docker Compose еднократната услуга `migrate` изчаква PostgreSQL да премине проверката за изправност и
изпълнява `python scripts/migrate.py`. API сървърът и вътрешният работен възел се стартират само след успешното
приключване на тази услуга; неуспешна миграция предотвратява стартирането им. При самостоятелно
внедряване трябва да се изпълни `cd backend && python scripts/migrate.py` преди API сървъра или работните възли.
Скриптът обновява базата данни до последната ревизия и проверява дали е достигната очакваната крайна
ревизия (head). API сървърът проверява независимо ревизията в PostgreSQL при стартиране и спира работа при несъответствие.

## 3. Поток на автентификация и оторизация

```text
1. User → POST /api/auth/login (username + password over TLS; the server checks it against the salted hash with Werkzeug check_password_hash)
2. API Server → verifies credentials → generates JWT with unique jti → sets httpOnly 'auth_token' cookie
3. Browser → subsequent API requests automatically transmit httpOnly cookie
4. Server → verify_token() middleware → checks Redis jti revocation blacklist → DB role lookup → authorizes
5. Logout → POST /api/auth/logout → clears cookie + blacklists jti in Redis (TTL = remaining token lifetime)
```

- **Ограничение на честотата при вход.** Отчитат се само неуспешните опити за вход (OWASP, NIST SP 800-63B): 5 неуспешни опита в рамките на минута заключват потребителското име, а 100 неуспешни опита за 10 мин заключват клиентския адрес (429 `ERR_RATE_LIMIT_EXCEEDED` с `Retry-After`). Успешните влизания никога не се ограничават, така че цяло училище зад един общ адрес може да влезе едновременно; успешният вход изчиства неуспешните опити за съответното потребителско име, но не и тези за адреса. Когато Redis не може да отчете опита, входът се отказва с `ERR_SERVICE_BUSY` (503), вместо ограничението да се прескочи. Зад балансьор на натоварването или прокси сървър всеки вход идва от адреса на проксито: преди внедряване зад такъв компонент задайте за него `set_real_ip_from` и `real_ip_header` във `frontend/nginx.conf` (коментирания блок там), иначе лимитът по адрес отчита целия сайт като един клиент. Проверката чрез PBKDF2 се изпълнява във вградения пул от нишки на gevent (`utils.threadpool.run_blocking`): `hashlib` освобождава GIL по време на хеширане, така че останалите заявки на същия работен възел продължават да се обслужват, а размерът на пула ограничава колко хеша се изчисляват едновременно.
- **Обхват на правата за жури.** `jury_access_required` извлича състезанието от обекта, посочен в URL адреса (задача, етап, решение, потребител), и отхвърля обект без състезание или такъв от състезание, различно от `challenge_id` в URL адреса; изпратеният от извикващия `challenge_id` никога не дава оторизация за даден обект. Само маршрути, които не посочват обект (регистрация на състезател), го четат от JSON тялото на заявката.
- **Единствен администратор.** Частичен уникален индекс (`uq_users_single_admin`) позволява само един ред с роля `admin`; API сървърът никога не създава и не изтрива администратора, нито дава или отнема ролята му, а `scripts/setup-admin.py` подменя на място идентификационните данни на този профил.
- **Нулиране на пароли.** Единственото правило се определя в `utils.access.password_reset_refusal`: администраторът може да нулира паролата на всеки профил освен на своя собствен, а член на журито – само на състезатели от поверено му състезание преди неговото начало. `GET /api/admin/users` връща това за всеки ред като `can_reset_password`, което управлява потребителския интерфейс.
- **Финализиране.** Полетата `is_finalized` и `reveal_results` на даден етап се променят единствено чрез `POST .../finalize` и `PUT .../reveal-results`; обновяването на етап отхвърля и двете полета. Грешките при финализиране назовават състезателите само по псевдоним. Кога е възможно финализирането, се определя от правило за резултатите (вижте „Правила за резултатите“ по-долу).

### Правила за резултатите (`services/contest_rules.py`)

Всяко правило, което определя резултат, се намира в този единствен модул и всеки маршрут, заявка и услуга го извиква; видимостта на резултатите остава в `utils/score_visibility.py`.

- **Краен срок.** Изпращането на решения по дадена задача приключва в края на нейния етап (или в края на състезанието, ако няма етап) плюс `DEADLINE_GRACE_PERIOD_SECONDS`; изпълнение, изпратено по-късно, никога не се зачита. Отговорите за задачи го съдържат като `submission_deadline`.
- **Зачитано изпълнение.** Избраното финално решение; ако няма такова – най-добрият публичен резултат, след това по-бързото изпълнение и накрая по-ранното решение. Частните резултати никога не определят кое изпълнение се зачита – нито преди, нито след разкриването им; след разкриването се показва частният резултат на зачетеното изпълнение. Едно и също подреждане обслужва както избора в Python (`counted_run`), така и двете прозоречни функции в SQL (преизчисляването на класацията и експорта на резултатите), а автоматичен тест проверява дали те съвпадат.
- **Финален избор.** Състезателят може да променя избора си по дадена задача до 5 мин след крайния срок или след началото на последното му изпълнение, изпратено преди срока – което от двете настъпи по-късно; прозорецът остава отворен, докато такова изпълнение все още чака или се изпълнява. `GET /api/tasks/<id>/submissions` изпраща на състезателите този прозорец и зачетеното изпълнение като `final_selection`, така че страницата не изчислява нито едното от двете.
- **Финализиране.** Етап или състезание може да се финализира, след като крайният срок и неговият гратисен период са изтекли, никое изпълнение на състезател по задачите му не чака и не се изпълнява (тестовите изпълнения на екипа и базовите бележници не се броят) и прозорецът за финален избор на всеки състезател е затворен; за състезанието тестовите етапи се пропускат. В противен случай маршрутите за финализиране връщат 409 с първото неизпълнено условие: `ERR_STAGE_NOT_ENDED` или `ERR_COMPETITION_NOT_ENDED` и `ERR_FINAL_SELECTION_OPEN` с `available_at`, `ERR_EVALUATIONS_PENDING` с `count`. `GET /api/challenges/<id>/finalize-status` докладва същото за състезанието и за всеки етап, а диалоговият прозорец за финализиране го показва и държи бутона за финализиране неактивен дотогава.

## 4. Конвейер за изпращане на решения и сигурност на изолираната среда

```text
1. User uploads .ipynb → POST /api/challenges/<id>/parse-notebook
2. User selects code cells → POST /api/tasks/<id>/submit
3. Server: every route creates submissions through one function, `services.submission_service.create_submission`: registration, window and readiness gates, then pre-execution AST validation (IPython magic stripping, banned_imports check). Rejected code returns diagnostics without creating a Submission or consuming quota; accepted code passes the quota checks (the daily limit resets at midnight in the challenge timezone; baselines and `failed_infra` platform failures never count) and the limit of active runs per competitor → creates the Submission → dispatches the Celery evaluation job at its fair-share priority (see "Evaluation queue" below; an enqueue failure marks it `failed_infra`)
4. Worker Node: picks up job → ensures task Docker image (lavbench_task_<id>) is compiled → seeds the run directory (submission script + task data snapshot) into the sandbox via put_archive
5. Hardened Sandbox Container: launches execution with zero-trust security parameters
6. Competitor Code: executes inside container → writes submission.parquet output (pulled back via get_archive)
7. Worker Evaluation Engine: evaluates submission.parquet against labels.parquet server-side (or runs evaluator.py) → updates Submission status & scores → publishes SSE event → invalidates leaderboard cache
```

**Задачи с файлове.** Режимът на оценяване (`evaluation_mode`) на задачата е `notebook` (горният конвейер) или `file`; той може да се променя, докато състезател не изпрати решение по задачата (`ERR_TASK_MODE_LOCKED`, 409). При задача с файл не се изпълнява код на ученика:

1. Ученикът изпраща решение от работното пространство (`POST /api/tasks/<id>/submit-workspace`). За даден ученик и задача в един момент може да се обработва само едно изпращане на файлово решение (`ERR_SUBMIT_LOCKED`, 429, с `Retry-After`); останалите задачи не се блокират. Заключването е валидно 60 сек. и заявката го подновява, докато работи, така че при срив на уеб процеса то се освобождава в рамките на минута. LavBench изисква от `export/metadata` на nanoColab размера и sha256 хеша на `<folder>/submission.parquet` и `<folder>/solution.ipynb`, извършва проверките за квота и дублиране по този хеш, приключва транзакцията в базата данни и едва тогава предава поточно и двата файла едновременно чрез суровия експорт, като сверява всеки от тях с метаданните му и ограничава размера до `NANOCOLAB_EXPORT_MAX_BYTES` (20 MiB) по време на поточното предаване. Работното пространство и двата пътя идват от сървъра (записа за работното пространство на ученика и `Task.folder_name`), никога от заявката. При прекъсване на nanoColab администратор може да включи аварийното качване за задачата (`PUT /api/tasks/<id>/emergency-upload`, с посочена причина и запис в одитния журнал), след което учениците качват същите два файла към `POST /api/tasks/<id>/submit-file`.
2. Преди да бъде създаден запис в базата данни и без отворена транзакция, Parquet файлът се проверява спрямо етикетите изцяло в краткотраен дъщерен процес (`services/parquet_check_child.py` чрез `utils/limited_process.py`): уеб процесът никога не чете Parquet файлове. Дъщерният процес получава чиста среда, ограничения за процесорно и реално време (`SUBMISSION_CHECK_TIME_LIMIT_SECONDS`) и ограничение за памет, оразмерено спрямо идентификаторите в етикетите – от `SUBMISSION_CHECK_MEMORY_MB` до горната граница `SUBMISSION_CHECK_MAX_MEMORY_MB`. Достигането на ограничение отхвърля файла; всеки друг неуспех на проверката е платформена грешка (`ERR_SUBMISSION_CHECK_FAILED`, 503, с `Retry-After`), която се записва в журналите, не изразходва квота и никога не сваля уеб процеса. Дъщерният процес първо прочита футъра: ограниченията за размер при оценяване, колоните за идентификатори от прост тип (цяло число, число с плаваща запетая, низ, булева стойност, времеви отпечатък или дата), както и колоните за идентификатори и предсказания, необходими за метриките или персонализирания оценител. След това прилага три граници, взети от етикетите, така че евентуална бомба при декомпресиране се отхвърля още преди разширяване на данните. Броят на редовете трябва да съвпада с броя на идентификаторите в етикетите. Колоната за идентификатори може да заема най-много некомпресирания размер при етикетите (броя на идентификаторите по дължината на най-дългия идентификатор плюс 4 байта, или по 8 байта за числа) плюс една осма и 64 KiB и се чете със запазване на речника ѝ, така че повтаряща се стойност остава един запис. Никой идентификатор не може да е по-дълъг от най-дългия идентификатор в етикетите, а идентификаторите трябва да са уникални. При решения за извличане на информация границите за размер и дължина на `doc_id` се пропускат, тъй като решението изброява и нерелевантни документи; те се ограничават от `MAX_PARQUET_ROWS`. Едва тогава дъщерният процес прочита всяка колона на партиди от по 1024 реда под ограничението `MAX_PARQUET_DECODED_BYTES` и сравнява точното множество от идентификатори чрез Arrow. Всеки уеб процес изпълнява най-много `SUBMISSION_CHECK_CONCURRENCY` проверки едновременно (`ERR_SUBMISSION_CHECK_BUSY`, 503, с `Retry-After`). Идентификаторите от етикетите и техните статистики се изграждат веднъж за всяка версия на етикетите при качването им и се кешират в `UPLOAD_FOLDER/label_ids/v<format>/<labels sha256>`, така че кеш, записан в по-стар формат, се пренебрегва и се изгражда наново; кешът се почиства, когато никоя задача вече не използва тези етикети. Етикети, които биха изисквали повече памет от горната граница, се отхвърлят още при качване (`ERR_LABELS_TOO_LARGE`, 413, с `limit`). Файл, който не премине проверката, получава `ERR_SUBMISSION_FILE_INVALID` (422) само с бройки и не изразходва квота. Всяко отхвърляне от дъщерния процес съдържа машинен код `reason` (например `row_count` с `rows` и `ids` или `ids_mismatch` с `expected_ids`, `missing_ids` и `unexpected_ids`) редом с английското обяснение в `detail`: клиентът показва текста от `api_reasons.<reason>`, попълнен с тези стойности, така че преведеното съобщение никога не съдържа текст на английски; `detail` остава за журналите и като резервен вариант. Същото важи за `ERR_BASELINE_SUBMISSION_INVALID`, `ERR_BASELINE_SUBMISSION_MISMATCH`, `ERR_HF_ZIP_INVALID` и `ERR_ENVIRONMENT_PACKAGE_TOO_LARGE`.
3. `create_submission` прилага същите проверки за достъп и готовност, както при клетките. Под заключването за изпращане функцията отхвърля Parquet файл, чийто sha256 хеш ученикът вече е изпращал по тази задача (`ERR_SUBMISSION_DUPLICATE`, 409), освен ако предишното решение не е завършило с платформена грешка (`failed_infra`). Файловете се преместват в `UPLOAD_FOLDER/submission_files/<submission id>/`, а в решението се записват `artifact_path`, `artifact_sha256`, `artifact_size`, `notebook_path`, `notebook_sha256`, `origin` и `workspace_meta`. Всеки маршрут указва стойността на `origin`, която създава: `cells` за `/submit`, `workspace`, `emergency_upload` и `baseline` за изпълненията на базови решения.
4. Задачите с файлове винаги се насочват към `cpu_queue`. Единствената точка на разклонение в изпълнителя (`run_eval_submission`) пропуска образа и изолираната среда: работният възел изтегля Parquet файла от `GET /api/worker/submission-artifact/<id>` с правото за достъп `submission_artifact` за съответния опит, проверява отново неговия sha256 хеш (при несъответствие оценяването се проваля като `failed_infra`) и преминава към същата стъпка за оценяване, както при изходния файл от бележник. Стъпката за оценяване изчислява публичния и частния резултат заедно, с по един процес за персонализиран оценител на всяка различна конфигурация на опциите за метриките, и времето ѝ се измерва на едно място като `evaluation_time_ms` – показва се само на администраторите и журито и никога не се използва за класиране. И в двата режима надзорният механизъм отпуска на работещото решение неговото време за изпълнение (1.5 пъти времевото ограничение) плюс бюджет за оценяване от 120 сек. и по `CUSTOM_EVALUATOR_TIME_LIMIT_SECONDS` за всяко стартиране на оценител, така че решение, което все още се оценява, никога не бива маркирано като `failed_infra`. Всеки Parquet файл, който работният възел чете, се декодира на партиди от по 1024 реда и четенето спира при достигане на `MAX_PARQUET_DECODED_BYTES`.

### Опашка за оценяване (справедливо разпределение)

Едни и същи правила важат за задачи с бележници и задачи с файлове; `services.submission_service` ги съдържа на едно място.

- **Без отказ заради натоварване.** Никое изпращане не се отхвърля заради дълга опашка. Единствено предпазната горна граница на брокера – `EVALUATION_QUEUE_CEILING` чакащи съобщения на опашка (по подразбиране 5000) – отхвърля изпълнение (`ERR_QUEUE_FULL`, 503, с `Retry-After`); тя защитава Redis, а не работните възли.
- **Активни изпълнения на състезател.** Всеки състезател може да има най-много `MAX_ACTIVE_RUNS_PER_USER` чакащи в опашката или текущи изпълнения (по подразбиране 2), преброени общо за всички задачи, в двата режима и във всички състезания. Следващо изпращане се отхвърля с `ERR_TOO_MANY_ACTIVE_RUNS` (429, с `limit`): без запис в базата данни и без изразходване на квота. `create_submission` го проверява под заключването за изпращане редом с квотата; при решения с файлове проверката се прави и преди експорта. Заключването за изпращане вече е едно на потребител (`submit_lock:user_<id>`), тъй като ограничението обхваща всички състезания. Изпълненията на базови решения и тестовите изпълнения на администратори и жури нямат такова ограничение.
- **Приоритет.** При насочване всяко изпълнение получава приоритет в брокера – по една и съща схема за решения с бележници и с файлове, както и за повторните опити на базови решения от надзорния механизъм:

  | Приоритет | Изпълнения |
  | :--- | :--- |
  | 0 | Базови решения и тестови изпълнения на администратори и жури |
  | 1 | Състезатели без използвано днес изпълнение по тази задача |
  | 2 | Състезатели с 1-2 използвани днес изпълнения по тази задача |
  | 3 | Състезатели с 3-5 използвани днес изпълнения по тази задача |
  | 4 | Състезатели с 6 или повече използвани днес изпълнения по тази задача |

  „Използвани днес“ брои изпълненията, които се отчитат към квотата (без базови решения и без `failed_infra`) от полунощ в часовата зона на състезанието, както при дневния лимит. Работните възли поемат първо по-ниските числа за приоритет и запазват реда на изпращане в рамките на един приоритет. Транспортът за Redis на Celery поддържа отделен списък за всяка стъпка на приоритет; приложението задава `priority_steps` на `0..4` и `queue_order_strategy` на `priority` (стъпките по подразбиране в kombu `0, 3, 6, 9` биха поставили приоритети 0 и 1 в един и същ списък). Всеки работен възел трябва да изпълнява един и същ код, тъй като даден работен възел е консуматор само на списъците за собствените си стъпки.
- **Оценяване след крайния срок.** Всичко, изпратено преди крайния срок (плюс `DEADLINE_GRACE_PERIOD_SECONDS`), се оценява, независимо колко време отнема изпразването на опашката: съобщенията за оценяване никога не изтичат и чакащо в опашката изпълнение никога не се прекратява поради изтекло време, докато съобщението му чака. При насочване опитът се добавя в множество в Redis (`eval:pending`), а при поемане от работен възел се премахва оттам и се записва часът на поемане. Надзорният механизъм прекратява чакащо изпълнение (`failed_infra`, без изразходване на квота) само когато след 10 мин опитът му не е нито сред чакащите, нито в брокера (чрез обхождане на списъците на опашките и на непотвърдените съобщения), така че загубено съобщение освобождава слота на състезателя до няколко минути. Поето изпълнение, чийто контейнер не е стартирал в рамките на твърдия времеви лимит в Celery плюс 5 мин, се прекратява като изгубен работен възел. Финализирането изчаква опашката (вижте „Правила за резултатите“).
- **Натоварен Redis.** Когато Redis не може да отговори на заявката за заключване при изпращане, подаването получава `ERR_SERVICE_BUSY` (503, с `Retry-After`) вместо `ERR_SUBMIT_LOCKED`; не се създава нищо.

Базовото решение на задача с файл е нейният скрит файл `baseline_submission.parquet`, който при качване се проверява по същия начин като ученически файл (`ERR_BASELINE_SUBMISSION_INVALID`, 422) и се оценява по същия път. Журито и администраторите изтеглят Parquet файла и бележника на решението от `GET /api/submissions/<id>/files/parquet` и `.../files/notebook`; докато състезанието е двойно сляпо, имената на файловете за журито съдържат псевдонима, а никога истинското име. Разпределените членове на журито и администраторите могат да изтеглят всеки файл на задачата, включително скритите, по всяко време – дори преди началото; състезателите никога не получават достъп до скрити файлове. При решения на един и същ ученик с равни резултати се зачита по-ранното.

### Параметри за изолация на контейнера с изолирана среда

Кодът на състезателя се изпълнява в Docker контейнер с нулево доверие (zero-trust) и строги ограничения на ядрото на Linux:

| Параметър | Цел и гаранция за сигурност |
| :--- | :--- |
| `--network none` | Напълно деактивира мрежата на контейнера — предотвратява изнасяне на данни и външни сокет повиквания. |
| `--cap-drop ALL` | Премахва всички привилегии (capabilities) на ядрото на Linux — блокира сурови (raw) сокети, `mount()`, `ptrace()` и ескалация на привилегии. |
| `--read-only` | Монтира кореновата файлова система само за четене — кодът на състезателя не може да променя системни изпълними файлове или библиотеки. |
| `--no-new-privileges` | Предотвратява ескалация на привилегиите на процеса чрез SUID изпълними файлове. |
| `--tmpfs /tmp:noexec,nosuid,size=128m` | Временна директория в паметта с ограничен размер, в която не могат да се изпълняват бинарни файлове и която не заема дисково пространство на хоста. |
| `--memory-swap` = лимит на RAM | Деактивира swap паметта — гарантира незабавно прекратяване от OOM механизма на ядрото при превишаване на лимита на RAM. |
| `--pids-limit 64` | Ограничава общия брой процеси за защита от fork бомби. |
| `--ulimit nofile=256:256` | Ограничава броя на отворените файлови дескриптори. |
| `--cpus` | Ограничава броя на CPU ядрата за контейнер (`CPU_CORES_PER_TASK` / `GPU_CORES_PER_TASK`). |
| `--storage-opt size` | Задължителна квота за записваемия коренов слой на контейнера (`WORKER_SANDBOX_STORAGE_OPT`, по подразбиране `8g`). Оценяването спира с грешка, ако драйверът за съхранение на Docker не може да я приложи. |

> **Известно ограничение:** `WORKER_SANDBOX_STORAGE_OPT` покрива само записваемия коренов слой на
> контейнера. Отделният анонимен том за всяко изпълнение, монтиран в `/app` (rw), е извън тази
> квота и **няма дискова квота**; кодът на състезателя може да го запълни до достигане на дисковия лимит
> на хоста. Паметта, CPU, броят процеси и реалното изминало време остават ограничени, а свободното
> пространство в `TASK_IMAGES_DIR` (`MIN_BUILD_DISK_GB`) се следи по време на изграждане на образи,
> но тези механизми не ограничават `/app`.

### Структура на постоянното съхранение

Изолираните среди не получават никакви пътища от хоста освен папките на Hugging Face за собствената им задача в режим само за четене (вж.
„Данни от Hugging Face“ по-долу). Образите на задачите, кешът на Hugging Face и работната директория на работния възел се съхраняват в **именувани томове** на Docker,
монтирани на фиксирани пътища в контейнера
(`/var/lib/lavbench/task_images`, `/var/lib/lavbench/hf_cache`, `/var/lib/lavbench/workspace`):

- **Режим с Docker** (`scripts/deploy-worker.sh`): именувани томове `lavbench_task_images`,
  `lavbench_hf_cache`, `lavbench_workspace`, създавани автоматично при внедряване.
- **Compose** (`docker-compose.yml`): `task_images_data`, `workspace_data` плюс споделения
  том `hf_cache`, монтирани на същите пътища в контейнера.
- **CI**: работният възел за оценяване използва локални за CI задачата именувани томове със същата структура.
- **Локален режим с micromamba**: работният възел се изпълнява като процес на хоста и използва обикновени директории на хоста
  (`TASK_IMAGES_DIR`, `HF_CACHE_DIR`, `LAVBENCH_WORKSPACE_DIR`) — без участието на Docker томове.

### Изолирана среда `/app`: анонимен том за всяко изпълнение

Всяко решение получава еднократен анонимен Docker том, монтиран в `/app` (rw). Работният възел
прехвърля директорията за изпълнение в него чрез `put_archive` преди стартирането на контейнера и
изтегля обратно резултата с `get_archive` след това; томът се премахва заедно с контейнера.
Метаданните на tar архива се нормализират за потребителя на изолираната среда (uid/gid 65534, директории 0777, файлове 0644 + битове за изпълнение),
така че процесът без root права да може да чете и пише в `/app`. Това премахва изцяло нуждата от директно монтиране на пътища от хоста —
демонът на хоста никога не трябва да разрешава път от страната на работния възел, поради което един и същ
код за изпълнение работи при среди с Docker, Docker Compose, CI и micromamba. Етикетите (`labels.parquet`)
никога не се записват в изолираната среда; те остават от страната на сървъра. Директорията за изпълнение съдържа кода,
публичните файлове на задачата в `data/`, както и твърди връзки към същите файлове редом до кода, така че бележникът
чете `train.csv` по точно същия начин, както от папката на задачата в работното си пространство.

Всеки контейнер на изолираната среда и неговият том носят етикетите `lavbench.sandbox`, `lavbench.attempt`,
`lavbench.time_limit` и `lavbench.deadline`. Процес на работен възел, който прекъсне по средата на изпълнението (прекратяване поради недостиг на памет,
повторно внедряване), никога не премахва своята изолирана среда, затова всеки работен възел за оценяване почиства Docker хоста при
стартиране и след това на всяка минута със собствен Docker клиент, така че дъщерните процеси от пула, разклонени по-късно, никога
не споделят неговия сокет (всеки дъщерен процес също освобождава евентуално наследения клиент). Контейнер се премахва, след като
измине времето от стартирането му плюс времевото ограничение плюс 10 мин (а за контейнер, който така и не е стартирал – след един час
зареждане на началните данни), така че продължителното копиране на данните никога не съкращава самото изпълнение. Когато изпълнение бъде принудително прекратено, изчистено или спре поради изтекло време,
сървърът отбелязва опита му като приключил в Redis (`attempt:ended:<attempt id>`) и следващото почистване премахва
изолираната среда незабавно. Докато изолираната среда работи, ключът `sandbox:live:<attempt id>` съществува, а принудително прекратено изпълнение, чиято
изолирана среда е все още жива, продължава да се брои към активните изпълнения на състезателя, така че прекратяването на изпълнение не може да се
използва за стартиране на друго, докато първото все още работи.

Принудителното прекратяване на самия процес на работния възел поради недостиг на памет кара Celery да достави изпълнението повторно
(`acks_late`). Всяко доставяне се преброява в Redis (`eval_delivery:<attempt id>`) и броячът се
изчиства при приключване на доставянето, освен при повторен опит от Celery (същото изпълнение отново), така че се натрупват само доставянията,
чийто процес е прекъснал. След надхвърляне на
`EVALUATION_MAX_DELIVERIES` (по подразбиране 3) изпълнението приключва като `failed_infra`, вместо да бъде доставяно повторно
до безкрайност.

### Данни от Hugging Face
Всяка задача може да има един ZIP архив за Hugging Face, съдържащ единствено `models/<org>/<name>/...` и
`datasets/<org>/<name>/...` — папките, които записва `hf download <repo> --local-dir`. Администраторите и
журито го качват чрез `PUT /api/tasks/<id>/hf-zip` (сурово тяло на заявката, задължителен `Content-Length`, до
`HF_ZIP_MAX_BYTES`, 10 GiB); `DELETE` го премахва. Уеб сървърът проверява само централния указател на архива:
без дублирани, абсолютни пътища, `..` или обратни наклонени черти, без връзки или специални файлове, без криптиране, само съхранени без компресия (stored)
или компресирани с deflate записи, коефициент на компресия най-много 200, съответствие с правилата на nanoColab за пътища, най-много 50,000
записа, преброени от самия указател (не само от крайния запис), най-много 2,000 видими файла
(ограничението за брой файлове в пакета, налагано дори без работни пространства) и поне един файл в папка на модел или
набор от данни. Скритите записи (всеки сегмент, започващ с `.`, например
`.cache/huggingface/` и `.gitattributes`) се пропускат и преброяват (`hf_skipped_count`), без да се
отхвърля архивът; обявените размери на останалите файлове не трябва да надвишават `HF_ZIP_MAX_BYTES`
(`hf_unpacked_bytes`). Грешки: `ERR_HF_ZIP_TOO_LARGE` (413, с `limit`), `ERR_HF_ZIP_INVALID`
(422, с машинен код `reason` като `outside_folders` или `case_clash`, пътя във `file` и
английския текст в `detail`), а когато работните пространства на състезанието
са включени — `ERR_HF_FOLDER_CONFLICT` (409, с `folder` и заглавието на другата задача в `detail`) за
папка, която присъства в друга задача от същата среда с различни файлове (при качване се сравняват размерите и CRC сумите,
а при сглобяване на пакета — SHA-256), както и `ERR_ENVIRONMENT_PACKAGE_TOO_LARGE` (413, с
очаквания размер или брой файлове в `detail` и `limit`, и `reason` `package_size` или
`package_files`), когато пакетът би надхвърлил ограничението си в байтове или
от 2,000 файла. Тези изчисления използват колоните на задачата (`hf_unpacked_bytes`, `hf_file_count`,
`hf_folders`); указателят на ZIP архива се чете повторно само когато две задачи с един и същ собственик споделят папка
от различни ZIP архиви, така че уеб заявките никога не разархивират нищо друго.

ZIP архивът се съхранява по веднъж за всеки хеш в `UPLOAD_FOLDER/hf/<sha256>.zip`; при качване на байтове, които вече са
съхранени, временният файл се изтрива и се запазва наличният. Инсталиранията за един собственик на среда (етап
или състезание без етапи) се изпълняват под едно общо заключване в Redis, споделено с файловете с данни на задачите,
а поставянето или изтриването на съхранен ZIP архив взима заключване за съответния хеш. Всяко изпълнение на бележник записва
хеша на ZIP архива на задачата при изпращане за изпълнение (`Submission.hf_zip_sha256`); заменен или премахнат ZIP архив се изтрива само
когато никоя задача и никое изпълнение в опашката или в ход не сочи към него, а ежедневната задача `tasks.sweep_upload_store`
изтрива изостаналите архиви. ZIP архивът се заключва заедно с публичните файлове след публикуване, пропуска се в
резервните копия и в експортите на състезания (експортът записва неговия sha256 хеш, размер и папки, а импортираната задача
носи флаг `hf_zip_not_imported` до качване или премахване на архива). Задача, чийто ZIP архив
липсва на сървъра — например след възстановяване от резервно копие — показва `ERR_HF_ZIP_MISSING`. Запазването му
планира изпълнение на базовия бележник (вж. „Качване на данни за задачата“).

Работните възли изтеглят ZIP архива при първото изпълнение на бележник, което се нуждае от него, чрез
`GET /api/worker/hf-zip/<sha256>` с правото за достъп `hf_zip`, издавано само за хеша,
записан при изпълнението — така текущото изпълнение запазва данните си, дори ако ZIP архивът на задачата бъде подменен по време на работа. Времевите ограничения в Celery за изпълнението
се увеличават с 60 сек. плюс две преминавания през ZIP архива при скорост 20 MiB/s (`utils.metadata.hf_prep_seconds`;
10 GiB добавят около 18 мин), като изчакването за заключването `flock` за съответния хеш
(`HF_CACHE_DIR/.locks/<sha256>.lock`) използва същия бюджет от време. Преди изтеглянето работният възел проверява
свободното място в `HF_CACHE_DIR` спрямо размера на ZIP архива плюс разархивирания му размер плюс 1 GiB; ако не достига,
първо пуска почистването на неизползвани кешове (кеш със задържано заключване никога не се премахва) и проверява отново.
Изтеглянето е поточно с проверка
на размера и sha256 хеша, след което архивът се разархивира във временна папка, като се пропускат скритите записи,
отхвърля се всеки файл, по-голям от обявения му размер или с невалидна CRC сума, и накрая папката се преименува на
`HF_CACHE_DIR/<sha256>/`. Неуспехът се отчита като платформена грешка (`failed_infra`): журналът на изпълнението показва един
общ ред, а причината се записва в журнала на работния възел. Неуспех при самите данни (грешка при изтегляне, несъответствие в размера или
хеша, липсващ или невалиден ZIP архив) задава също `ERR_HF_DATA_SYNC_FAILED` за задачата, подобно на
грешка при синхронизиране на файл на задачата. Следващото изпълнение, което подготви текущия ZIP архив на задачата, изчиства този код: неговият
доклад `running_inference` пренася `hf_ready`, а сървърът премахва `ERR_HF_DATA_SYNC_FAILED`,
когато изпълнението е записало текущия `hf_zip_sha256` на задачата (базовият бележник, който пропуска проверката за готовност, прави
това след поправянето на данните). Диск за кеша, на който мястото все още не достига след почистването, изтекло време за изчакване на заключване или
друга грешка в кеша са проблем на работния възел: изпълнението приключва неуспешно като `failed_infra`, работният възел записва
причината в журнала си (при пълен диск — „Worker disk full“ със свободното и необходимото място, изпращано заедно с журналите на работния възел),
а задачата не се блокира.
Всяко изпълнение обновява времевия отпечатък на `<sha256>/.last-used`; почистването при стартиране на работен възел и ежедневното почистване премахват
кешове, които не са използвани в продължение на `HF_CACHE_UNUSED_DAYS` (14) дни, както и недовършени папки на повече от един ден.

В изолираната среда папките `models/` и `datasets/` за този хеш се монтират само за четене в `/models` и `/datasets`,
така че от работната директория `/app` пътищата `../models/<org>/<name>` и
`../datasets/<org>/<name>` сочат на същото място, както от `/workspace/<folder>/` в работното пространство. Никой друг
хеш не е видим. Работен възел, който се изпълнява в контейнер (обичайният случай, при който той стартира съседни контейнери
през сокета на Docker), прочита идентификатора на контейнера си от източника на монтирания `/etc/hostname`,
намира тома зад `HF_CACHE_DIR`, като инспектира собствения си контейнер, и го монтира чрез
подпът на тома (Docker API 1.45, Docker 26 и по-нови); при директно монтиран кеш се използва съответният път от хоста,
а работен възел върху самия хост монтира директно `HF_CACHE_DIR`. В контейнер, който не може да бъде
разпознат или инспектиран, или когато няма монтиране, покриващо `HF_CACHE_DIR`, изпълнението приключва като платформена
грешка, вместо да се прави опит за отгатване на пътя. В изолираната среда променливите
`HF_HUB_OFFLINE`, `HF_DATASETS_OFFLINE` и `TRANSFORMERS_OFFLINE` се задават със стойност `1`. Самото оценяване никога не чете
файлове от Hugging Face, а при задачите с файлове не се стартира изолирана среда, така че техните данни от Hugging Face достигат единствено до работните пространства.

### Почистване на остарели директории
Работните директории за решения (`LAVBENCH_WORKSPACE_DIR`) обикновено се премахват в блок `finally`,
но принудително спрян или рестартиран работен възел може да остави некриптирани файлове. Две допълващи се процедури за почистване изтриват всяка
поддиректория, която не е променяна през последните 24 часа:
1. **Стартиране на работния възел** (tasks.py `_stale_dir_sweep_on_start`, `celeryd_init`, сериализирано чрез fcntl);
2. **Ежедневен график (beat)** (`task-dir-sweep-daily`).

## 5. Конвейер за изграждане на образи за задачите и класификация на грешките

Всяка задача поддържа постоянна директория за изграждане в `TASK_IMAGES_DIR/task_{id}/`. Образът на контейнера получава етикет `lavbench_task_{task_id}_{hash}`, където хешът обхваща базовия образ, пакетите, публичните файлове на задачата и кода на оценителя (скритите файлове никога не попадат в образа, така че нов файл с етикети никога не води до повторното му изграждане). Изпълненията, насочени преди и след редакция, намират всяко своя собствен образ, вместо взаимно да преизграждат образите си, а успешното изграждане на образ премахва образите на задачата от по-стари конфигурации, които не се използват от никоя изолирана среда.

### Последователност при изграждане на образ:
```text
[Base Image Pull] ──> [APT Packages Install] ──> [Pip Requirements Install] ──> [Task Files]
```

### Класификация на грешките при изграждане на образ (`ERR_IMAGE_BUILD_FAILED`):
1. **Невалиден базов образ**: Несъществуващ таг или грешка 404/401 при изтегляне от регистъра.
2. **Неуспешно разрешаване на APT пакети**: Сгрешени имена на Ubuntu пакети или липсващи apt хранилища.
3. **Конфликт в Pip зависимостите**: Несъвместими версии на Python библиотеки или липсващи инструменти за компилиране на C/C++ (`build-essential`).
4. **Изчерпване на дисковото пространство**: Свободното дисково пространство на хоста е под `MIN_BUILD_DISK_GB` (лимит от 5 GB).

### Възстановяване след грешки при изграждане и отстраняване на проблеми:
- Неуспешните изграждания на образи или проблеми със средата се записват като **регистър на проблеми** — списък с машинно четими кодове в `task.problem_codes` (напр. `ERR_TASK_FILE_SYNC_FAILED`, `ERR_HF_DATA_SYNC_FAILED`, `ERR_TASK_BUILD_FAILED`, `ERR_BASELINE_FAILED`, `ERR_BASELINE_SUBMISSION_MISMATCH`). Всеки непразен регистър блокира новите решения с `ERR_TASK_NOT_READY` (403), а всяка първопричина се превежда от страната на клиента.
- Отговорите за организаторите и журито (`problem_codes` във формуляра на задачата и в списъка със задачи) добавят при всяка заявка кодове, прочетени от файловете на задачата: `ERR_TASK_LABELS_MISSING`, `ERR_BASELINE_SUBMISSION_MISSING` (при задачи с файлове) и `ERR_HF_ZIP_MISSING`. Те се показват, но не се записват в базата данни. Двата кода за липсващи файлове освен това блокират проверката за готовност, тъй като `services.task_data.readiness_problems` захранва както тази проверка, така и списъка с проблеми: задача без етикети или задача с файл без своето базово решение отхвърля решенията от състезатели, жури и администратори с `ERR_TASK_NOT_READY` (без запис в базата данни и без изразходване на квота), а при задача с файл — още преди файлът да бъде извлечен или проверен; изпълненията на базовия бележник пропускат тази проверка, както и досега. `ERR_HF_ZIP_MISSING` служи единствено за информиране на организаторите и журито.
- `problem_fields` (в отговорите за организаторите и журито, `Task.problem_fields`) съдържа полетата за съобщения, записани към даден код, групирани по код. `ERR_BASELINE_SUBMISSION_MISMATCH` съхранява кода `reason` и стойностите от проверката (например `ids_mismatch` с `expected_ids`, `missing_ids` и `unexpected_ids` или `row_count` с `rows` и `ids`), както и английското обяснение в `detail`; записите за проблеми към `ERR_TASK_NOT_READY` пренасят същите полета, а формулярът на задачата и списъкът със задачи ги попълват в преведения текст.
- Регистърът се управлява според жизнения цикъл: докладваните от работен възел грешки при изграждане на образ добавят кодове, успешното изграждане на образ изчиства кодовете от тази група, изпълнение, преминало успешно през стъпка за синхронизиране, изчиства грешката за тази стъпка дори когато образът е взет от кеша (`running_inference` изчиства `ERR_TASK_FILE_SYNC_FAILED`, а оценено изпълнение изчиства `ERR_TASK_LABELS_SYNC_FAILED`), а промените в конфигурацията на средата (базов образ, настройки за apt/pip) изчистват остарелите проблеми при изграждане.
- Всяко приключване на изпълнение на базов бележник (доклад от работен възел, непоето изпълнение, изгубен работен възел, превишен времеви лимит в Celery, принудително прекратяване, изчистване на опашката от администратор) обновява състоянието на задачата на едно място — `services.baseline_service`: успешно завършилото изпълнение премахва `ERR_BASELINE_FAILED`, а неуспешното, прекратеното или изчистеното го задава. Изпълнение на базов бележник със статус `failed_infra` (непоето изпълнение, изгубен работен възел, проблем с GPU или Docker, времеви лимит в Celery) първо се повтаря като ново изпълнение на базов бележник най-много 2 пъти (общо 3 опита), всяко със собствен запис за решение и журнали. Повторен опит не се прави, когато задачата вече има друг код за проблем (всяко изпълнение би се провалило по същия начин) или когато брокерът е отхвърлил поставянето в опашката; запазването на задачата планира ново изпълнение на базовия бележник.
- Създаването на задача, запазването на формуляра ѝ и всяко качване или премахване на файл с данни или архив за Hugging Face планират изпълнението на базовия бележник, вместо да го поставят веднага в опашката: `services.baseline_service.schedule_baseline` записва маркер в Redis (`baseline_due:<task id>`, уникален токен за всяка промяна, 10 мин валидност), изтрива приключилите изпълнения на базовия бележник и изпраща `tasks.run_due_baseline` към опашката `internal` с отложено изпълнение от 60 сек. Само задачата, чийто токен все още съвпада с маркера, поставя базовия бележник в опашката — така запазване на формуляра, последвано от няколко качвания, води до едно-единствено изпълнение около минута след последната промяна и до едно изграждане на образ. По-старите изпълнения на базовия бележник, които вече са в опашката или се изпълняват, запазват записите си, така че техните работни възли все още могат да отчетат резултат; докато маркерът съществува, техният изход не променя нищо. При липса на Redis или на брокера базовият бележник се поставя в опашката незабавно. Тъй като вътрешният работен възел изпраща тези изпълнения (както и повторните опити за базовия бележник от страна на наблюдателя), неговият списък с разрешени променливи включва `EVALUATION_SPLIT_SECRET` и настройките за изпращане (`DEFAULT_TIME_LIMIT_SEC`, `DEFAULT_RAM_LIMIT_MB`, `DEFAULT_PUBLIC_EVAL_PERCENTAGE`, `CUSTOM_EVALUATOR_TIME_LIMIT_SECONDS`, времевите ограничения на Celery); изпращане, което не може да състави метаданните си, отбелязва изпълнението като `failed_infra`, вместо да го остави в опашката.
- Ако заключване за изграждане на образ остане блокирано поради прекъсване на работен възел, администратор може да го изчисти на хоста на работния възел с помощната функция `clear_build_lock(task_id)` (`tasks/task_modules/image_builder.py`) — напр. от обвивката на работния възел. За това няма бутон в интерфейса или администраторски HTTP маршрут.
- Запазването на съществени промени по задачата (базов образ, настройки за apt/pip, файлове на задачата, код на оценителя) променя хеша на конфигурацията на образа (`_config_hash`), така че следващото изграждане на образ (отложеното изпълнение на базовия бележник или следващото решение) създава нов образ, вместо да използва кеширания. Всяко изпълнение сверява образа си с текущата конфигурация на задачата дори когато на работния възел вече съществува образ със съответния етикет, така че промените в пакетите, базовия образ и файловете достигат до всеки работен възел. Неуспешно изграждане на образ никога не се връща към по-стар образ.
- Докато друго изпълнение на същия работен възел изгражда образа, текущото изпълнение изчаква това изграждане, вместо да се провали – най-много `IMAGE_BUILD_WAIT_SECONDS` (по подразбиране 900) и никога по-дълго от времето, което остава от мекия времеви лимит в Celery след приспадане на времевото ограничение на изпълнението и резерва за оценяване; конфигурирано изчакване, по-дълго от мекия лимит минус една минута, се съкращава при стартиране с предупреждение. Изграждащият процес подновява заключването си (`docker_build:lock:<host>:<task id>`, за 120 сек., подновявано на всеки 40 сек.), така че ако прекъсне, заключването се освобождава до две минути и чакащото изпълнение само изгражда образа.

### Качване на данни за задачата
Формулярът на задачата запазва метаданните заедно единствено с малките файлове в една multipart заявка: базовия бележник,
бележника с решението и оценителя, всеки с размер най-много `MAX_NOTEBOOK_BYTES` (16 MiB). След това всеки файл с данни —
публичен или скрит, включително `labels.parquet` и `baseline_submission.parquet` — се предава поточно
в отделна заявка като сурово тяло към `PUT /api/tasks/<id>/files/<name>?visibility=public|hidden`
(изисква се `Content-Length`, до `TASK_FILE_MAX_BYTES`, 10 GiB, `ERR_FILE_TOO_LARGE` с
`limit`); `DELETE` на същия път премахва файла. Multipart маршрутите отхвърлят полета с файлове с данни
(`ERR_INVALID_UPLOAD_FORMAT`). Качването на файлове и ZIP архивът за Hugging Face споделят `utils/uploads.py`: първо се изпълняват проверките за права, име,
брой (5 файла) и заключвания. Тялото на заявката трябва да бъде от тип `application/octet-stream` или
`application/zip` (`ERR_UPLOAD_CONTENT_TYPE`, 415) със зададен `Content-Length` (`ERR_UPLOAD_LENGTH_REQUIRED`,
411) и да се побира в свободното място на диска за качвания минус 2 GiB (`ERR_UPLOAD_NO_SPACE`, 507, със свободното пространство в
`limit`). След това транзакцията приключва и тялото се хешира при записа му във временен файл
в `UPLOAD_FOLDER/.incoming/`, на същата файлова система, така че самото инсталиране да се сведе до преименуване; при прекъсване на
връзката се връща `ERR_UPLOAD_INTERRUPTED`. Следват специфичните за файла проверки: на етикетите в ограничения
дъщерен процес, на `baseline_submission.parquet` при задача с файл спрямо текущите етикети (при несъответствие се отхвърля с
`ERR_BASELINE_SUBMISSION_INVALID`, 422, с `detail`), а за публичните файлове при включени работни пространства —
на очакваните ограничения за пакета. Новите етикети никога не се отхвърлят заради съхраненото базово решение: те се
инсталират, а съхраненото базово решение се проверява спрямо тях впоследствие; ако то вече не им съответства, се задава
`ERR_BASELINE_SUBMISSION_MISMATCH`, докато не бъдат качени съвместимо базово решение или съвместими етикети, или
докато някой от двата файла не бъде премахнат. Едва тогава, под заключване в Redis за собственика на средата (при заетост:
`ERR_UPLOAD_STORE_BUSY`, 503, с `Retry-After`), файлът се преименува на окончателното му място и се записва с
неговия размер и sha256 хеш, като заменя съществуващ файл със същото име; отхвърлено или прекъснато качване оставя
съхранения файл непокътнат. Качването на скрит файл след публикуване изисква права на администратор и посочена причина (`reason`), както и досега. Всяка
промяна се записва в одитния журнал (при замяна се записват също предишната видимост и размер) и планира
изпълнение на базовия бележник. Преместването на задача в друг етап проверява ограниченията за пакета и папките на Hugging Face за целевия собственик
под неговото заключване, задържано до потвърждаване на транзакцията за преместването, така че две премествания към един и същ собственик не могат да преминат
едновременно.

Ежедневната задача `tasks.sweep_upload_store` (в опашката `internal_long`) премахва временни файлове в
`.incoming/` на повече от 6 ч, файлове в папка на задача, които не присъстват в записа на задачата (останали след
срив между преименуването и потвърждаването на транзакцията), след като навършат 6 ч, както и съхранени ZIP архиви за Hugging Face, към които нищо
не сочи. Експортите на състезания записват само файловете, описани в задачата, а резервните копия пропускат `.incoming/`.

### Подмяна на файлове и етикети на задачата (уникално `saved_name`)
Качените ресурсни файлове на задачата (включително `labels.parquet`) се съхраняват под име `saved_name` с префикс UUID
(разширението се запазва). Тъй като повторното качване на файл със *същото* публично файлово име
сменя `saved_name`, кешът за ресурси от страната на работния възел — който използва `saved_name` като маркер
за промяна — засича подмяната и синхронизира наново новите байтове в `TASK_IMAGES_DIR/task_{id}/data`
(както и в кеша `labels/`, достъпен само на хоста), а при изграждане на образ се вграждат новите данни. Маршрутът за качване пази
точно по един запис в манифеста за всяко файлово име и изтрива подменения файл от диска след
успешно качване.

### Изтегляне от работните възли и цялост на данните
При всяко качване в записа в `Task.files` се съхраняват `size_bytes` и `sha256` на записаните байтове,
изчислени при самото записване на файла; при импортиране на състезание и двете стойности се преизчисляват от разархивираните файлове.
Работните възли получават тези записи с всяко решение, а крайната точка за файлове на работните възли
(`GET /api/worker/tasks/{id}/files/{name}`) изпраща `Content-Length` и, когато хешът е известен,
`ETag`, равен на sha256. Крайната точка допуска по 120 заявки в минута за адрес на работен възел, така че
паралелните задания да могат да синхронизират всички файлове на своите задачи.

Всяко изтегляне от работен възел (кеш за ресурси, кеш за етикети само на хоста, контекст за изграждане на образ) минава през
`utils.worker_utils.download_file`; изграждане на образ, което чете директно от директорията за качени файлове, копира
през `copy_file_verified`, като прилага същите стъпки от 2 до 4:

1. Тялото се предава поточно на блокове от 1 MiB (`stream=True`) във временен файл в целевата
   директория и се хешира в движение, така че използваната памет не расте с размера на файла. Временните
   файлове започват с `.download-`: моментната снимка на ресурсите в изпълнителя ги пропуска, а генерираният
   `.dockerignore` изключва тях, `.locks/` и достъпната само на хоста директория `labels/` от контекста за изграждане
   на образ.
   `WORKER_DOWNLOAD_TIMEOUT` ограничава установяването на връзката и всяко изчакване на данни, а не целия трансфер.
2. Размерът и sha256 се сравняват със записаните стойности; при разминаване временният файл се
   изтрива, целевият файл остава непокътнат, а заданието завършва неуспешно по съществуващия път за грешка
   при синхронизация (`ERR_TASK_FILE_SYNC_FAILED` за файлове на задачи и изграждания на образи,
   `ERR_TASK_LABELS_SYNC_FAILED` за етикети). Записите отпреди
   въвеждането на тази проверка нямат sha256: те се проверяват по размер, а urllib3 все така отхвърля тяло,
   по-кратко от `Content-Length`.
3. Провереният файл заменя целевия чрез атомарно извикване на `os.replace`.
4. Записите в споделените кешове `TASK_IMAGES_DIR/task_{id}/` държат изключително заключване с `fcntl.flock` върху
   `task_{id}/.locks/<dir>-<name>.lock` (извън `data/`, която се вгражда в образа). Процесите
   и контейнерите на работните възли на един хост споделят тома, а оттам и заключването: второ задание
   изчаква и след това използва готовия файл наново, когато неговият sha256 съвпада, вместо да го изтегля повторно. Синхронизация,
   която вече знае, че кешираното копие е остаряло (неговото `saved_name` се е променило), пропуска тази проверка. Времето
   за изчакване е ограничено (`DOWNLOAD_LOCK_MAX_WAIT`, 900 сек.); при изтичането му заданието завършва неуспешно по същия
   път за грешка при синхронизация. Заключването не е предназначено за мрежови файлови системи.

Манифестът на ресурсите (`task_{id}/.assets.json`, съдържащ `saved_name` за всеки кеширан файл) се обновява
под собствено заключване: всяка синхронизация го прочита наново, слива своите промени и го подменя през уникален
временен файл. Неуспешен запис на манифеста се записва в журналите и не проваля изпълнението, тъй като кешираните
файлове вече са проверени; следващата синхронизация ги проверява отново.

## 6. Архитектура на модула за оценяване

`services/evaluation/` поддържа 44 стандартни метрики за оценяване в 12 категории задачи, заедно с персонализирани скриптове за оценяване (`evaluator.py`).

| # | Категория | Ключове на метриките | Основно предназначение |
| :--- | :--- | :--- | :--- |
| 1 | **Класификация** | `accuracy`, `f1`, `precision`, `recall`, `cohen_kappa`, `matthews_corrcoef` | Класификация с дискретни целеви стойности. |
| 2 | **Вероятностни** | `auc_roc`, `logloss`, `brier_score` | Калибрирани непрекъснати оценки на увереност. |
| 3 | **Регресия** | `rmse`, `mse`, `mae`, `r_squared`, `mape`, `median_ae` | Измерване на грешката при непрекъснати целеви стойности. |
| 4 | **Етикетиране на последователности (NER)** | `seqeval_f1`, `seqeval_precision`, `seqeval_recall` | Класификация на именувани обекти на ниво токени. |
| 5 | **Генеративен NLP** | `bleu`, `rouge`, `rouge_l`, `meteor`, `chrf`, `ter` | Превод, резюмиране и генериране на текст. |
| 6 | **Извличащо отговаряне на въпроси (QA Extractive)** | `exact_match`, `f1` (припокриване на думи) | Припокриване на токени при четене с разбиране. |
| 7 | **Откриване на обекти** | `map_50`, `map_75`, `map_50_95`, `recall` (откриваемост на рамки) | Оценяване чрез IoU и mAP на ограничаващи рамки. |
| 8 | **Сегментация** | `mean_iou`, `dice`, `pixel_accuracy` | Оценяване на семантични маски и маски на отделни обекти. |
| 9 | **Ключови точки** | `oks`, `pck` | Сходство на ключови точки на обекти при определяне на поза. |
| 10 | **Качество на изображения** | `psnr`, `ssim` | Метрики за реконструкция и възстановяване на изображения. |
| 11 | **Качество на аудио** | `snr`, `mel_lsd`, `si_sdr` | Качество при обработка на реч и аудио. |
| 12 | **Клъстеризация** | `adjusted_rand_index`, `normalized_mutual_info`, `adjusted_mutual_info`, `v_measure` | Сходство при неконтролирано групиране в клъстери. |
| + | **Извличане на информация** | `ndcg_k`, `recall_k`, `mrr` | Метрики за извличане на информация и ранжиране. |
| * | **Персонализирани оценители** | Динамично `METRIC_NAME`, връщано от `evaluator.py` | Персонализирани скриптове за оценяване в специфични области (`evaluate(df_sub, df_labels, options)`). |

**Персонализираните оценители** се изпълняват върху CPU работния възел за оценяване като ограничен подпроцес, еднакво за задачи с бележник и за задачи с файл (`services/evaluation/custom_evaluator.py`): използват се собственият Python и библиотеки на работния възел, временна папка, съдържаща единствено предсказанията, етикетите и опциите, чиста среда, изградена от нулата без `WORKER_*` или други тайни, както и ограничения чрез `resource`, зададени преди изпълнението на кода на оценителя (адресно пространство `CUSTOM_EVALUATOR_MEMORY_MB`, 1024; процесорно и реално време `CUSTOM_EVALUATOR_TIME_LIMIT_SECONDS`, 300, след което се прекратява цялата група процеси). Резултатът трябва да е речник от крайни числа с размер до `MAX_EVALUATOR_RESULT_BYTES`; при всяка грешка състезателят получава общо съобщение, а изходът на оценителя се записва единствено в журнала на работния възел. Подпроцесът няма изолация на мрежата или файловата система: оценителите се качват само от администратори и жури, като всяко качване се записва в одитния журнал.

## 7. Конвейер за типовете на API и архитектура на валидацията

```text
Pydantic v2 Schemas + spectree @api.validate Decorators
       │
       ▼
  /apidoc/openapi.json (auto-generated OpenAPI 3.0 spec)
       │
       ▼
  openapi-typescript (npm run generate-api-types)
       │
       ▼
  src/types/api.d.ts (Full TypeScript declaration file)
       │
       ▼
  tsc --noEmit (npm run check-types — validates JSDoc annotations & component props)
```

Спецификацията е достъпна през nginx на `:80/apidoc/openapi.json` (не е необходим порт на хоста към сървърната част). CI задачата `docker-build` генерира наново `api.d.ts` от работещия стек и спира с грешка при всяко разминаване; записаните в хранилището снимки на спецификацията в `docs/source/api/` се обновяват с `make -C docs fetch-spec`. Цялостното поведение (автентификация, матрица на ролите, ограничения на честотата, резервни копия, SSE) се проверява от `scripts/api_smoke_test.py` спрямо работещия Docker Compose стек в CI.

### Стандартизация на грешките (`err()` и `check_error_codes.py`)
Всички отговори за грешки от сървърното API използват `err("ERR_CODE", status_code)`, като връщат `{"error": "<message>", "code": "ERR_CODE"}`. Скриптът `backend/scripts/check_error_codes.py` проверява в CI дали всеки код за грешка е регистриран в `DEFAULT_ERROR_MESSAGES` и преведен в езиковите файлове за `en` и `bg`.

## 8. Архитектура за поточно предаване в реално време чрез SSE

Пет сървърни крайни точки използват Server-Sent Events (SSE):

| Крайна точка | Събитие | Условие за задействане |
| :--- | :--- | :--- |
| `/api/challenges/<id>/leaderboard/live` | `{"event": "update"}` | Периодичната задача за класацията (на всеки 20 сек.) е преизчислила състезание с променени резултати. |
| `/api/submissions/<id>/logs/live` | Редове от журнала на изпълнението | Изход stdout/stderr на живо от изолираната среда на работния възел, предаван поточно само докато решението се изпълнява. |
| `/api/admin/backups/live` | `{"event": "update"}` | Приключило е автоматично или ръчно резервно копие. |
| `/api/admin/submissions/queue/live` | `{"event": "update"}` | Настъпила е промяна в опашката за оценяване. |
| `/api/challenges/<id>/environment/live` | `{"event": "update"}` | Настъпила е промяна в nanoColab среда на състезанието (раздел 12). |

Събитията, различни от редовете от журнала, не пренасят данни. При всяко събитие клиентът извлича наново съответната REST крайна точка чрез TanStack Query с ограничаване на честотата, така че поредица от събития предизвиква само една заявка, а сървърът никога не съставя отделен отговор за всеки наблюдател. Всеки поток изпраща поле `retry:` и коментар за поддържане на връзката, времето за изчакване при неактивност има случайно отклонение, за да не изтичат потоците едновременно, а сесията към базата данни на заявката се освобождава преди началото на поточното предаване.

Списъците с решения не се предават поточно. Списъкът на състезателя се опреснява със заявки на всеки 15 до 30 сек. (със случайно закъснение при всяко запитване), докато някое от неговите решения е в опашката или се изпълнява, като при неуспешни запитвания закъснението се удвоява до максимум 2 мин, а в останалото време не се правят запитвания; потокът с журналите на отвореното решение е основният сигнал за неговото приключване.

Обновяването на класацията достига едновременно до всяка отворена страница с класация, затова всеки раздел извлича данните наново след случайно закъснение от 0 до 10 сек. вместо след около 2 сек.; при 400 раздела това свали 95-ия персентил на повторните заявки от 5.8 сек. на 0.16 сек. Скритият раздел пропуска опресняването и извлича данните наново едва когато бъде показан отново. Маршрутът за класацията връща модел на Pydantic вместо речник, така че spectree го сериализира без обхождане на всяка стойност (около 14 от общо 48 ms процесорно време на заявка). Приключилото решение показва съхранените си журнали; за изпълняващите се решения Redis пази последните `SSE_LOG_MAX_LINES` реда от журнала (по подразбиране 500) за `SSE_LOG_TTL` сек. (по подразбиране 3600), така че повторно свързал се наблюдател да може да навакса.

Капацитетът на SSE се управлява от `SSE_MAX_GLOBAL` (по подразбиране `2000` едновременни връзки за цялата платформа) и `SSE_MAX_PER_USER` (по подразбиране `15` на клиент). Docker Compose зарежда `.env` в услугите, така че и двете стойности могат да бъдат презаписани там.

## 9. Архитектура за съхранение на автоматични и ръчни резервни копия

| Вид резервно копие | Честота на задействане | Политика за съхранение | Управление и ограничения на API |
| :--- | :--- | :--- | :--- |
| **Автоматично резервно копие (пълно)** | На всеки **6 часа**, както по време на активни състезания, така и при престой. | Пази **3-те** най-нови (`BACKUP_RETENTION_COUNT`). По-старите се изтриват автоматично. | Управлява се от системата (`auto_YYYYMMDD_HHMMSS.tar.gz`). Не може да се изтрива ръчно през API (връща HTTP 403). |
| **Автоматично резервно копие (само база данни)** | На всеки **20 минути** по време на активни състезания. | Пази **18-те** най-нови (`BACKUP_DB_RETENTION_COUNT`) — около 6 часа история, която стига назад до предишното пълно резервно копие. | Управлява се от системата (`auto_db_YYYYMMDD_HHMMSS.tar.gz`). Не може да се изтрива ръчно през API (връща HTTP 403). |
| **Ръчно резервно копие** | Задейства се при поискване чрез бутона **„Създай резервно копие сега“**. | Пази се **за неограничено време**. Никога не се изтрива автоматично от процедурите за почистване. | Управлява се от администратор (`manual_YYYYMMDD_HHMMSS.tar.gz`). Може да се изтегля или изтрива през административния панел. |

Пълните архиви съдържат дъмп на PostgreSQL (`pg_dump`) и файловете от `uploads/` във файл `.tar.gz`; архивите само на базата данни съдържат единствено дъмпа. Ротираните файлове с журнали (`*.log.N`) се пропускат, както и `uploads/environment_packages/` (временни пакети на nanoColab, които се изграждат наново от файловете на задачата), `uploads/hf/` (ZIP архиви на Hugging Face, които администраторът качва отново; експортите записват техния sha256 хеш) и `uploads/.incoming/` (качвания в ход). Архивите използват най-бързото ниво на gzip (`gzip -1`), тъй като данните на задачите в повечето случаи вече са компресирани; `pg_dump` е ограничен от `BACKUP_TIMEOUT` (600 сек.), а `tar` — от по-голямата стойност измежду `BACKUP_TIMEOUT` и `BACKUP_UPLOADS_TIMEOUT` (3600 сек.). Преди всяко резервно копие сървърът изисква свободно дисково пространство поне два пъти по-голямо от предишното резервно копие от същия вид и не по-малко от `MIN_BACKUP_DISK_GB`. Неуспешно автоматично резервно копие не се отчита като завършено и се прави нов опит при следващата 20-минутна проверка, като по всяко време в опашката или в изпълнение може да има най-много едно автоматично резервно копие.

## 10. Разпределяне и ограничаване на хардуерните ресурси на работните възли

По време на първоначалната настройка (`make setup-worker`) работните възли проверяват общия брой CPU ядра (`nproc`), RAM паметта (`/proc/meminfo`) и наличните GPU (`nvidia-smi`), като заделят 1 CPU ядро и 4 GB RAM за системни нужди.

### Формула за ограничаване на RAM паметта по време на изпълнение:
```text
budget_mb = (GPU_RAM_PER_TASK_GB if task.gpu_required else CPU_RAM_PER_TASK_GB) * 1024

if task_ram <= budget_mb:
    use task_ram as-is
elif task_ram <= budget_mb * RAM_CLAMP_FACTOR (1.05):
    clamp container memory to budget_mb (log warning)
else:
    reject task → Celery retry → dead-letter queue (/api/admin/dead-letters)
```

Маршрутите за работните възли (`/api/worker/*`, `/api/workers/logs`) прилагат ограничение на честотата за всеки работен възел по идентификатора в неговия подписан токен, така че няколко работни възела зад един адрес или NAT получават пълния лимит поотделно; заявка без валиден подпис се ограничава по своя адрес. Изчисляването на ключа проверява подписа, но не изразходва еднократната стойност (nonce) на токена.

При сигнала `worker_ready` работните възли записват своята хардуерна спецификация в клиента за координация на Redis (`worker_spec:<hostname>`), а фонова нишка я опреснява на всеки `WORKER_HEARTBEAT_SECONDS` (по подразбиране 30) заедно с опашките, чийто консуматор е работният възел, и `last_seen`. Ключът изтича след един ден; работният възел се отчита като на линия, докато последният му сигнал за активност е на възраст под `WORKER_HEARTBEAT_STALE_SECONDS` (по подразбиране 90). Сигналите за активност захранват `GET /api/status` и `GET /api/admin/system-status` (раздел 11). Регистрацията на работните възли се управлява изцяло от сигнали — не съществува отделна задача за регистрация.

## 11. Крайни точки за състояние и проверка за изправност

| Крайна точка | Достъп | Предназначение |
| :--- | :--- | :--- |
| `GET /api/health` | Публичен | Работоспособност: база данни, кеш Redis, брокер Redis и диск. Връща 200 или 503 и се използва от проверките за изправност на контейнерите. Никога не проверява работните възли, така че липсващ работен възел не може да представи API като неработещо. |
| `GET /api/status` | Публичен | Обобщено състояние за външни проверки на достъпността, използващо стойностите на Statuspage `operational`, `degraded_performance`, `partial_outage` и `major_outage`. Кешира се за `STATUS_CACHE_SECONDS` (по подразбиране 30). |
| `GET /api/admin/system-status` | Администратор, жури | Подробните данни зад състоянието: опашки, работни възли и брой решения. Показва се в панела **Работни възли и опашки** на административния панел, който го запитва на всеки 15 сек. |

И двете крайни точки за състояние се изчисляват от сигналите за активност на работните възли, дължините на опашките в брокера и базата данни. Уеб процесите никога не извикват Celery `inspect`.

| Компонент | Правило |
| :--- | :--- |
| `api` | `major_outage`, когато базата данни или брокерът Redis са недостъпни, в противен случай `operational`. |
| `scoring` | `major_outage`, когато нито един работен възел на линия не е консуматор на `cpu_queue`; `partial_outage`, когато друга опашка за оценяване има чакащи съобщения, но няма консуматор на линия; `degraded_performance`, когато най-старото решение в опашката е чакало по-дълго от `STATUS_QUEUE_DEGRADED_SECONDS` (по подразбиране 600); в противен случай `operational`. |

Общото `status` приема най-тежкото състояние сред компонентите. Работният възел се счита за на линия, когато последният му сигнал за активност е на възраст под `WORKER_HEARTBEAT_STALE_SECONDS` (по подразбиране 90); работните възли изпращат сигнал за активност на всеки `WORKER_HEARTBEAT_SECONDS` (по подразбиране 30).

### Настройки за капацитет

- **Уеб процеси.** Gunicorn стартира `GUNICORN_WORKERS` процеса с gevent; Docker Compose задава стойността на `BACKEND_CPUS` (по подразбиране 4), по един на всяко CPU ядро от квотата на сървъра. Gunicorn поддържа неактивните връзки отворени за 75 сек. – по-дълго от 60 сек. при nginx, така че nginx никога не преизползва връзка, която Gunicorn затваря.
- **Ограничения на контейнерите.** PostgreSQL получава `DB_CPUS` (по подразбиране 2) и `DB_MEMORY` (по подразбиране 2 GiB); nginx получава `FRONTEND_CPUS` (по подразбиране 1) и 512 MiB. При прегледа бе измерено, че на стария лимит от 1 CPU PostgreSQL се насища при около 125 прочитания на състезание в секунда, а nginx на 0.5 CPU – при около 58 отговора с класация в секунда.
- **nginx.** Входната точка стартира по един работен процес на всяко CPU ядро от квотата (`NGINX_WORKER_PROCESSES`, зададен от `FRONTEND_CPUS`; стойността `auto` би преброила всички CPU ядра на хоста). `nginx.main.conf` задава `worker_rlimit_nofile 65536` и `worker_connections 8192`, а Docker Compose повишава лимита за файлови дескриптори на контейнера до 65536; всеки проксиран SSE поток заема два дескриптора. Отговорите на API се буферират (`proxy_buffering on`, до 256 KiB в паметта на отговор, без запис на диск), така че бавен клиент никога не задържа greenlet нишка на Gunicorn; SSE отговорите изключват буферирането чрез `X-Accel-Buffering: no`. nginx поддържа до 32 неактивни връзки към Gunicorn на работен процес (`upstream backend_api`).
- **Вътрешни работни възли.** Docker Compose стартира два вътрешни работни възела от една дефиниция: `celery_worker` (`-Q celery,internal`) за кратките периодични задачи (преизчисляване на класацията на всеки 20 сек., надзорен механизъм, проверка за резервни копия, отложени базови бележници, насочване на синхронизиране) и `celery_worker_long` (`-Q internal_long`) за `run_backup`, `sync_environment`, `reconcile_nanocolab_events` и `sweep_upload_store`, които могат да продължат почти час. Правилата в `task_routes` на Celery изпращат тези четири задачи към `internal_long`, така че създаването на резервно копие никога не заема слотовете за преизчисляване на класацията и периодичните съобщения за нея не изтичат в изчакване зад него. Само `celery_worker` насочва изпълнения, затова единствено той получава `EVALUATION_SPLIT_SECRET` и настройките за насочване.
- **Версии на работните възли.** Работните възли докладват своите стъпки за приоритет на опашките в сигнала за активност. Работен възел с различни стъпки (друга версия на LavBench или твърде стара, за да ги докладва) не поема изпълнения от всеки приоритет, затова панелът за работни възли и опашки го отбелязва с „Нужно е обновяване“, а сървърът записва предупреждение в журнала: обновявайте работните възли и сървъра заедно.
- **Връзки към Redis.** Всеки процес използва `BlockingConnectionPool` за всяка инстанция на Redis с `REDIS_POOL_MAX_CONNECTIONS` връзки (по подразбиране 200): когато всички са заети, извикващият код изчаква до `REDIS_POOL_TIMEOUT_SECONDS` (по подразбиране 2), вместо да се провали веднага. Проверките за сигурност отказват достъп при недостъпен Redis: токен, чието анулиране не може да бъде проверено, получава `ERR_AUTH_UNAVAILABLE` (503), а заявка, която ограничението на честотата не може да отчете, получава `ERR_SERVICE_BUSY` (503) – и в двата случая с `Retry-After: 5`. Анулиранията, записани в същия процес, продължават да се зачитат и без Redis. Четенето от кеша и на състоянието продължава работа при отказ на Redis.
- **Флагове за заключване.** `mode_locked` и `files_locked` се изчисляват само за изгледите на администратори и жури, откъдето се редактират задачи; изгледите за състезатели на състезание, задача или класация пропускат и двете заявки и ги показват като `false`. `mode_locked` за единична задача (проверяван при изпращане на решение и редакция на задача) е заявка с `EXISTS`, която спира при първото намерено решение на състезател.

## 12. Среди в nanoColab

LavBench управлява `/v1` API на nanoColab; nanoColab никога не извиква LavBench. Договорът за интерфейса е OpenAPI файлът на nanoColab, включен в `backend/tests/contracts/nanocolab-v1.openapi.json`, а останалите подробности са описани в `docs/source/ops/nanocolab-integration.md`. Когато `NANOCOLAB_API_URL` не е зададена, всеки маршрут за среда отговаря с `ERR_NANOCOLAB_DISABLED` (404), с изключение на `GET /api/environment/images`, който отговаря с `available: false`, така че администраторските формуляри да скрият секцията за работното пространство. Всеки отговор с данни за състезание съдържа `workspaces_enabled` (конфигуриран nanoColab и включени работни пространства за състезанието); страницата на задачата за учениците заявява нейната среда и отваря потока на живо само когато тази стойност е истина.

**Роли.** Администраторите избират настройката, публикуват и удължават срока; журито преглежда състоянието, подробностите и списъка с работни пространства за всяка среда (с псевдоними при двойно сляпо оценяване); учениците виждат по едно състояние на задача (не е отворена, подготвя се, готова, затворена или неизвестно, когато кешираното състояние е остаряло) и могат да я стартират след началото на етапа ѝ (преди това се връща `ERR_NOT_AVAILABLE`, както и за самата задача). GET маршрутите никога не извикват крайна точка на nanoColab, която извършва запис.

**Състояние.** Администраторите и журито виждат `off`, `uploading` (с процент), `preparing`, `ready`, `problem` (със съобщението от nanoColab само за администраторите; журито получава кода) или `unknown`, когато кешираната готовност е по-стара от `NANOCOLAB_STATUS_STALE_SECONDS`. Публикувана среда, която остане в състояние `preparing` по-дълго от `NANOCOLAB_PREPARING_ALERT_MINUTES`, получава флаг `alert: true`.

**Заключвания след публикуване.** Началото, изчислителните настройки, образът и датата за архивиране се фиксират; промяна в настройката се отхвърля, когато всички среди са публикувани (`ERR_ENVIRONMENT_LOCKED`), като списъкът със среди предава това състояние на формуляра чрез `setting_locked`; в противен случай се прилага само за непубликуваните; краят може само да се измества напред чрез удължаване с посочена причина преди текущия край плюс гратисния период (`ERR_EXTENSION_TOO_LATE`). Промените по публичните файлове на задачите, данните от Hugging Face и базовия бележник, както и преместването и изтриването на задачи се отхвърлят (`ERR_TASK_FILES_LOCKED`), същото важи и за преименуването на папка. До публикуването папката на задачата следва нейното заглавие, освен ако администратор не е задал името ѝ ръчно; автоматично генерирано име, което вече се използва в етапа, получава числова наставка (`-2`, `-3`, ...), докато заето ръчно зададено име се отхвърля (`ERR_TASK_FOLDER_TAKEN`). Скритите файлове (`labels.parquet`, `baseline_submission.parquet` и всеки файл, качен като скрит) и оценителят все още могат да бъдат подменяни, но само от администратор с въведена причина (`reason`), която се запазва в одитния запис; базовото решение на задача с файл се планира отново за проверка. Активираните среди в рамките на едно състезание не могат да се застъпват във времето, включително гратисния период след всеки край, тъй като всеки ученик разполага с един сървър в JupyterHub (`ERR_ENVIRONMENT_OVERLAP` – проверява се при включване на работните пространства, добавяне на етап или промяна на времето на етап).

**Маршрути.** `GET /api/environment/images` (администратор) връща `available`, образите, профилите и допустимия диапазон за `workspace_gib` (от 10 до 100 GiB минус ограничението за пакета `NANOCOLAB_PACKAGE_MAX_BYTES`, т.е. 90 по подразбиране; стойност по подразбиране 10). `GET /api/challenges/<id>/environments` (администратор, жури) извежда списък с всички среди заедно с тяхното състояние, `workspace_gib`, `data_gib` и `disk_gib`. Публикуването, удължаването на срока, списъкът с работни пространства, потокът на живо, както и маршрутите за средата на задачата и за нейното стартиране действат върху една конкретна среда. При отхвърлена стойност на настройка в тялото на грешката се посочва съответното поле `field` (например `workspace.workspace_gib`) и се включват допълнителни данни като `min`, `max`, `allowed` или `stages`.

**Локален стек.** `make dev-nanocolab` стартира локалния kind стек и API на nanoColab, както и LavBench с неговите работни възли, и извежда данните за вход на администратора; `make e2e-nanocolab` изпълнява тестовете за сценариите на администратор, ученик и жури срещу него; `make dev-nanocolab-down` го спира.
