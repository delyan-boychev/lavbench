# Системна архитектура и инфраструктура на LavBench

## 1. Общ преглед на системата

```text
Browser (React SPA) ──> Nginx (Port 80 / 443, HTTP(S) / SSE Reverse Proxy)
                            ├── Flask API Server (Port 5001, Gunicorn + gevent)
                            │     ├── PostgreSQL 15 (Primary Database)
                            │     ├── Redis (Celery Broker + Coordination: SSE pub/sub fan-out, worker_spec registry, submission fallback key, versioned leaderboard invalidations, dead-letter queue, GPU/build locks)
                            │     ├── Redis Cache (Private, server-only: leaderboard caches, locks, rate-limit counters, JWT blacklist — CACHE_REDIS_URL never given to external workers)
                            │     ├── Celery Beat (Periodic Scheduler: Backups, Watchdog)
                            │     └── Internal Celery Worker (System tasks only, inside Docker Compose, -Q celery,internal)
                            └── Remote Execution Workers (Celery evaluation-only workers: Docker container or host, consume cpu_queue)
                                  └── Sibling Sandbox Containers (--network none, --read-only, --cap-drop ALL)
```

## 2. Технологичен стек на компонентите

| Компонент | Технология | Роля и основни отговорности |
| :--- | :--- | :--- |
| **Клиентска част (Frontend)** | React 19 + Vite + Vanilla/Tailwind CSS | SPA с обновявания на живо чрез SSE, i18n (en/bg), JSDoc `@type` валидация (`tsc --noEmit`). |
| **API сървър** | Flask 3.1 + Gunicorn + gevent + spectree | REST API крайни точки, Pydantic v2 валидация на заявки/отговори, SSE поточно предаване на събития. |
| **Основна база данни** | PostgreSQL 15 | Потребители, състезания, етапи, задачи, решения, журнали за одит (`AuditLog`). |
| **Кеш и брокер** | Redis | Celery брокер на задачи + **клиент за координация** за цялото споделено състояние между машините: SSE pub/sub разпращане, регистър на спецификациите на работните възли (`worker_spec:<hostname>`), резервен ключ за решения, версионирани инвалидирания на класациите, опашка за необработени съобщения (dead-letter queue), заключвания за GPU и изграждане на образи, разпределени заключвания (за изпращане на решения и за класацията), броячи за ограничение на честотата, неуспешни опити за вход, отменени JWT токени и маркери за резервните копия. Устойчивостта чрез AOF и `noeviction` защитават задачите в опашката и тези гаранции. |
| **Самостоятелен кеш** | Redis (DB 1, `volatile-lru`, без устойчивост) | Самостоятелен, частен сървърен кеш за данни, които могат да се изчислят наново: кешове за класацията и за състоянието, списъци за повторно възпроизвеждане на журналите по SSE и състояние на решенията (`CACHE_REDIS_URL`). Когато се напълни, изхвърля най-отдавна използваните ключове с TTL, затова нищо в него не бива да е необходимо за коректността. Вътрешен контейнер — без порт към хоста; външните работни възли никога не получават този URL. |
| **Опашка със задачи** | Celery 5.4 | Асинхронно изпълнение на фонови задачи (оценяване на решения, изграждане на образи, резервни копия на базата данни). |
| **Планировчик** | Celery Beat | Периодични задачи (контрольор за заседнали решения, график за автоматични резервни копия). |
| **Работни възли** | Celery работен възел за оценяване | Работни възли **само за оценяване**, консумиращи `cpu_queue`; изпълняват кода на състезателя в съседни Docker контейнери с изолирана среда (`deploy-worker.sh` / `worker.env`). |

### Жизнен цикъл на миграциите на базата данни

В Docker Compose еднократната услуга `migrate` изчаква PostgreSQL да премине проверката за изправност и
изпълнява `python scripts/migrate.py`. API сървърът и вътрешният работен възел се стартират само след успешното
приключване на тази услуга; неуспешна миграция предотвратява стартирането им. При самостоятелно
внедряване трябва да се изпълни `cd backend && python scripts/migrate.py` преди API сървъра или работните възли.
Скриптът обновява познатите ревизии, приема наследена база без Alembic версия само когато отразената ѝ схема
съвпада точно с базовата, отхвърля разминавания или непознати ревизии и проверява дали е достигната
очакваната крайна ревизия (head). API сървърът проверява независимо ревизията в PostgreSQL при стартиране и
спира работа при несъответствие.

## 3. Поток на автентификация и оторизация

```text
1. User → POST /api/auth/login (username + SHA256(password))
2. API Server → verifies credentials → generates JWT with unique jti → sets httpOnly 'auth_token' cookie
3. Browser → subsequent API requests automatically transmit httpOnly cookie
4. Server → verify_token() middleware → checks Redis jti revocation blacklist → DB role lookup → authorizes
5. Logout → POST /api/auth/logout → clears cookie + blacklists jti in Redis (TTL = remaining token lifetime)
```

## 4. Конвейер за изпращане на решения и сигурност на изолираната среда

```text
1. User uploads .ipynb → POST /api/challenges/<id>/parse-notebook
2. User selects code cells → POST /api/challenges/<id>/submit
3. Server: Pre-execution AST validation (IPython magic stripping, banned_imports check). Rejected code returns diagnostics without creating a Submission or consuming quota; accepted code proceeds through rate/quota checks → creates Submission → dispatches Celery evaluation job
4. Worker Node: picks up job → ensures task Docker image (lavbench_task_<id>) is compiled → seeds the run directory (submission script + task data snapshot) into the sandbox via put_archive
5. Hardened Sandbox Container: launches execution with zero-trust security parameters
6. Competitor Code: executes inside container → writes submission.parquet output (pulled back via get_archive)
7. Worker Evaluation Engine: evaluates submission.parquet against labels.parquet server-side (or runs evaluator.py) → updates Submission status & scores → publishes SSE event → invalidates leaderboard cache
```

### Параметри за изолация на контейнера с изолирана среда

Кодът на състезателя се изпълнява в Docker контейнер с нулево доверие (zero-trust) и строги ограничения на ядрото на Linux:

| Параметър | Цел и гаранция за сигурност |
| :--- | :--- |
| `--network none` | Напълно деактивира мрежата на контейнера — предотвратява изнасяне на данни и външни сокет повиквания. |
| `--cap-drop ALL` | Премахва всички привилегии (capabilities) на ядрото на Linux — блокира сурови (raw) сокети, `mount()`, `ptrace()` и ескалация на привилегии. |
| `--read-only` | Монтира кореновата файлова система само за четене — кодът на състезателя не може да променя системни изпълними файлове или библиотеки. |
| `--no-new-privileges` | Предотвратява ескалация на привилегиите на процеса чрез SUID изпълними файлове. |
| `--tmpfs /tmp:noexec,nosuid,size=128m` | Временна директория в паметта с ограничен размер, в която не могат да се изпълняват бинарни файлове и която не заема дисково пространство на хоста. |
| `--memory-swap` = лимит на RAM | Деактивира swap паметта — гарантира незабавно прекратяване от OOM механизма на ядрото при превишаване на лимита на RAM. |
| `--pids-limit 64` | Ограничава общия брой процеси за защита от fork бомби. |
| `--ulimit nofile=256:256` | Ограничава броя на отворените файлови дескриптори. |
| `--cpus` | Ограничава броя на CPU ядрата за контейнер (`CPU_CORES_PER_TASK` / `GPU_CORES_PER_TASK`). |
| `--storage-opt size` | Задължителна квота за записваемия коренов слой на контейнера (`WORKER_SANDBOX_STORAGE_OPT`, по подразбиране `8g`). Оценяването спира с грешка, ако драйверът за съхранение на Docker не може да я приложи. |

> **Известно ограничение:** `WORKER_SANDBOX_STORAGE_OPT` покрива само записваемия коренов слой на
> контейнера. Отделният анонимен том за всяко изпълнение, монтиран в `/app` (rw), е извън тази
> квота и **няма дискова квота**; кодът на състезателя може да го запълни до достигане на дисковия лимит
> на хоста. Паметта, CPU, броят процеси и реалното изминало време остават
> ограничени, а свободното пространство в `TASK_IMAGES_DIR` (`MIN_BUILD_DISK_GB`) се следи по време на
> изграждане на образи, но тези механизми не ограничават `/app`.

### Структура на постоянното съхранение

Никакви пътища от хоста не се монтират директно (bind-mount) в работните възли или изолираните среди. Образите на задачите, кешът на Hugging Face и
работната директория на работния възел се съхраняват в **именувани томове** на Docker, монтирани на фиксирани пътища в контейнера
(`/var/lib/lavbench/task_images`, `/var/lib/lavbench/hf_cache`, `/var/lib/lavbench/workspace`):

- **Режим с Docker** (`scripts/deploy-worker.sh`): именувани томове `lavbench_task_images`,
  `lavbench_hf_cache`, `lavbench_workspace`, създавани автоматично при внедряване.
- **Compose** (`docker-compose.yml`): `task_images_data`, `workspace_data` плюс споделения
  том `hf_cache`, монтирани на същите пътища в контейнера.
- **CI**: работният възел за оценяване използва локални за CI задачата именувани томове със същата структура.
- **Локален режим с micromamba**: работният възел се изпълнява като процес на хоста и използва обикновени директории на хоста
  (`TASK_IMAGES_DIR`, `HF_CACHE_DIR`, `LAVBENCH_WORKSPACE_DIR`) — без участието на Docker томове.

### Изолирана среда `/app`: анонимен том за всяко изпълнение

Всяко решение получава еднократен анонимен Docker том, монтиран в `/app` (rw). Работният възел
прехвърля директорията за изпълнение в него чрез `put_archive` преди стартирането на контейнера и
изтегля обратно резултата с `get_archive` след това; томът се премахва заедно с контейнера.
Метаданните на tar архива се нормализират за потребителя на изолираната среда (uid/gid 65534, директории 0777, файлове 0644 + битове за изпълнение),
така че процесът без root права да може да чете и пише в `/app`. Това премахва изцяло нуждата от директно монтиране на пътища от хоста —
демонът на хоста никога не трябва да разрешава път от страната на работния възел, поради което един и същ
код за изпълнение работи при среди с Docker, Docker Compose, CI и micromamba. Етикетите (`labels.parquet`)
никога не се записват в изолираната среда; те остават от страната на сървъра.

### Почистване на остарели директории
Работните директории за решения (`LAVBENCH_WORKSPACE_DIR`) обикновено се премахват в блок `finally`,
но принудително спрян или рестартиран работен възел може да остави некриптирани файлове. Две допълващи се процедури за почистване изтриват всяка
поддиректория, която не е променяна през последните 24 часа:
1. **Стартиране на работния възел** (tasks.py `_stale_dir_sweep_on_start`, `celeryd_init`, сериализирано чрез fcntl);
2. **Ежедневен график (beat)** (`task-dir-sweep-daily`).

## 5. Конвейер за изграждане на образи за задачите и класификация на грешките

Всяка задача поддържа постоянна директория за изграждане в `TASK_IMAGES_DIR/task_{id}/`. Образът на контейнера получава етикет `lavbench_task_{task_id}`.

### Последователност при изграждане на образ:
```text
[Base Image Pull] ──> [APT Packages Install] ──> [Pip Requirements Install] ──> [HF Pre-Fetch & Task Files]
```

### Класификация на грешките при изграждане на образ (`ERR_IMAGE_BUILD_FAILED`):
1. **Невалиден базов образ**: Несъществуващ таг или грешка 404/401 при изтегляне от регистъра.
2. **Неуспешно разрешаване на APT пакети**: Сгрешени имена на Ubuntu пакети или липсващи apt хранилища.
3. **Конфликт в Pip зависимостите**: Несъвместими версии на Python библиотеки или липсващи инструменти за компилиране на C/C++ (`build-essential`).
4. **Изтекло време за изтегляне / грешка при автентификация в Hugging Face**: Прекъсване на мрежата, превишаване на лимита за време или липсващ `hf_api_key` за модели с ограничен достъп.
5. **Изчерпване на дисковото пространство**: Свободното дисково пространство на хоста е под `MIN_BUILD_DISK_GB` (лимит от 5 GB).

### Възстановяване след грешки при изграждане и отстраняване на проблеми:
- Неуспешните изграждания на образи или проблеми със средата се записват като **регистър на проблеми** — списък с машинно четими кодове в `task.problem_codes` (напр. `ERR_HF_DOWNLOAD_FAILED`, `ERR_TASK_BUILD_FAILED`, `ERR_BASELINE_FAILED`). Всеки непразен регистър блокира новите решения с `ERR_TASK_NOT_READY` (403), а всяка първопричина се превежда от страната на клиента.
- Регистърът се управлява според жизнения цикъл: докладваните от работен възел грешки при изграждане на образ добавят кодове, успешното изграждане изчиства кодовете, свързани с изграждането, успешното изпълнение на базовия бележник премахва `ERR_BASELINE_FAILED`, а промените в конфигурацията на средата (базов образ, настройки за apt/pip/Hugging Face) изчистват остарелите проблеми при изграждане.
- Ако заключване за изграждане на образ остане блокирано поради прекъсване на работен възел, администратор може да го изчисти на хоста на работния възел с помощната функция `clear_build_lock(task_id)` (`tasks/task_modules/image_builder.py`) — напр. от обвивката на работния възел. За това няма бутон в интерфейса или администраторски HTTP маршрут.
- Запазването на съществени промени по задачата (базов образ, настройки за apt/pip/Hugging Face, файлове на задачата, код на оценителя) публикува известие `task_rebuild` в Redis; слушателят за преизграждане на работния възел (`_rebuild_listener`) изтегля наново конфигурацията на задачата и извършва изграждане на образ с `force_rebuild=True`, заобикаляйки бързия път чрез хеш на конфигурацията. Ресурсите от Hugging Face се сверяват с най-новата ревизия в хранилището (повторна валидация чрез etag, изтеглят се само променените байтове) и образът се изгражда отново със свежите данни.

### Подмяна на файлове и етикети на задачата (уникално `saved_name`)
Качените ресурсни файлове на задачата (включително `labels.parquet`) се съхраняват под име `saved_name` с префикс UUID
(разширението се запазва). Тъй като повторното качване на файл със *същото* публично име
сменя `saved_name`, кешът за ресурси от страната на работния възел — който използва `saved_name` като маркер
за промяна — засича подмяната и синхронизира наново новите байтове в `TASK_IMAGES_DIR/task_{id}/data`
(както и в кеша `labels/`, достъпен само на хоста), а при изграждане на образ се вграждат новите данни. `update_task` пази
точно по един запис в манифеста за всяко публично файлово име и изтрива подменения файл от диска след
успешно потвърждаване на трансакцията.

## 6. Архитектура на модула за оценяване

`services/evaluation/` поддържа 44 стандартни метрики за оценяване в 12 категории задачи, заедно с персонализирани скриптове за оценяване (`evaluator.py`).

| # | Категория | Ключове на метриките | Основно предназначение |
| :--- | :--- | :--- | :--- |
| 1 | **Класификация** | `accuracy`, `f1`, `precision`, `recall`, `cohen_kappa`, `matthews_corrcoef` | Класификация с дискретни целеви стойности. |
| 2 | **Вероятностни** | `auc_roc`, `logloss`, `brier_score` | Калибрирани непрекъснати оценки на увереност. |
| 3 | **Регресия** | `rmse`, `mse`, `mae`, `r_squared`, `mape`, `median_ae` | Измерване на грешката при непрекъснати целеви стойности. |
| 4 | **Етикетиране на последователности (NER)** | `seqeval_f1`, `seqeval_precision`, `seqeval_recall` | Класификация на именувани обекти на ниво токени. |
| 5 | **Генеративен NLP** | `bleu`, `rouge`, `rouge_l`, `meteor`, `chrf`, `ter` | Превод, резюмиране и генериране на текст. |
| 6 | **Извличащо отговаряне на въпроси (QA Extractive)** | `exact_match`, `f1` (припокриване на думи) | Припокриване на токени при четене с разбиране. |
| 7 | **Откриване на обекти** | `map_50`, `map_75`, `map_50_95`, `recall` (откриваемост на рамки) | Оценяване чрез IoU и mAP на ограничаващи рамки. |
| 8 | **Сегментация** | `mean_iou`, `dice`, `pixel_accuracy` | Оценяване на семантични маски и маски на отделни обекти. |
| 9 | **Ключови точки** | `oks`, `pck` | Сходство на ключови точки на обекти при определяне на поза. |
| 10 | **Качество на изображения** | `psnr`, `ssim` | Метрики за реконструкция и възстановяване на изображения. |
| 11 | **Качество на аудио** | `snr`, `mel_lsd`, `si_sdr` | Качество при обработка на реч и аудио. |
| 12 | **Клъстеризация** | `adjusted_rand_index`, `normalized_mutual_info`, `adjusted_mutual_info`, `v_measure` | Сходство при неконтролирано групиране в клъстери. |
| + | **Извличане на информация** | `ndcg_k`, `recall_k`, `mrr` | Метрики за извличане на информация и ранжиране. |
| * | **Персонализирани оценители** | Динамично `METRIC_NAME`, връщано от `evaluator.py` | Персонализирани скриптове за оценяване в специфични области (`evaluate(df_sub, df_labels, options)`). |

## 7. Конвейер за типовете на API и архитектура на валидацията

```text
Pydantic v2 Schemas + spectree @api.validate Decorators
       │
       ▼
  /apidoc/openapi.json (auto-generated OpenAPI 3.0 spec)
       │
       ▼
  openapi-typescript (npm run generate-api-types)
       │
       ▼
  src/types/api.d.ts (Full TypeScript declaration file)
       │
       ▼
  tsc --noEmit (npm run check-types — validates JSDoc annotations & component props)
```

Спецификацията е достъпна през nginx на `:80/apidoc/openapi.json` (не е необходим порт на хоста към сървърната част). CI задачата `docker-build` генерира наново `api.d.ts` от работещия стек и спира с грешка при всяко разминаване; записаните в хранилището снимки на спецификацията в `docs/source/api/` се обновяват с `make -C docs fetch-spec`. Цялостното поведение (автентификация, матрица на ролите, ограничения на честотата, резервни копия, SSE) се проверява от `scripts/api_smoke_test.py` спрямо работещия Docker Compose стек в CI.

### Стандартизация на грешките (`err()` и `check_error_codes.py`)
Всички отговори за грешки от сървърното API използват `err("ERR_CODE", status_code)`, като връщат `{"error": "<message>", "code": "ERR_CODE"}`. Скриптът `backend/scripts/check_error_codes.py` проверява в CI дали всеки код за грешка е регистриран в `DEFAULT_ERROR_MESSAGES` и преведен в езиковите файлове за `en` и `bg`.

## 8. Архитектура за поточно предаване в реално време чрез SSE

Четири сървърни крайни точки използват Server-Sent Events (SSE):

| Крайна точка | Събитие | Условие за задействане |
| :--- | :--- | :--- |
| `/api/challenges/<id>/leaderboard/live` | `{"event": "update"}` | Периодичната задача за класацията (на всеки 20 s) е преизчислила състезание с променени резултати. |
| `/api/submissions/<id>/logs/live` | Редове от журнала на изпълнението | Изход stdout/stderr на живо от изолираната среда на работния възел, предаван поточно само докато решението се изпълнява. |
| `/api/admin/backups/live` | `{"event": "update"}` | Приключило е автоматично или ръчно резервно копие. |
| `/api/admin/submissions/queue/live` | `{"event": "update"}` | Настъпила е промяна в опашката за оценяване. |

Събитията, различни от редовете от журнала, не пренасят данни. При всяко събитие клиентът извлича наново съответната REST крайна точка чрез TanStack Query с ограничаване на честотата, така че поредица от събития предизвиква само една заявка, а сървърът никога не съставя отделен отговор за всеки наблюдател. Всеки поток изпраща поле `retry:` и коментар за поддържане на връзката, времето за изчакване при неактивност има случайно отклонение, за да не изтичат потоците едновременно, а сесията към базата данни на заявката се освобождава преди началото на поточното предаване.

Списъците с решения не се предават поточно. Списъкът на състезателя се опреснява със заявки на всеки 5 секунди, докато някое от неговите решения е в опашката или се изпълнява, и не се опреснява в останалото време. Приключилото решение показва съхранените си журнали; за изпълняващите се решения Redis пази последните `SSE_LOG_MAX_LINES` реда от журнала (по подразбиране 500) за `SSE_LOG_TTL` секунди (по подразбиране 3600), така че повторно свързал се наблюдател да може да навакса.

Капацитетът на SSE се управлява от `SSE_MAX_GLOBAL` (по подразбиране `2000` едновременни връзки за цялата платформа) и `SSE_MAX_PER_USER` (по подразбиране `15` на клиент). Docker Compose зарежда `.env` в услугите, така че и двете стойности могат да бъдат презаписани там.

## 9. Архитектура за съхранение на автоматични и ръчни резервни копия

| Вид резервно копие | Честота на задействане | Политика за съхранение | Управление и ограничения на API |
| :--- | :--- | :--- | :--- |
| **Автоматично резервно копие (пълно)** | На всеки **6 часа**, както по време на активни състезания, така и при престой. | Пази **3-те** най-нови (`BACKUP_RETENTION_COUNT`). По-старите се изтриват автоматично. | Управлява се от системата (`auto_YYYYMMDD_HHMMSS.tar.gz`). Не може да се изтрива ръчно през API (връща HTTP 403). |
| **Автоматично резервно копие (само база данни)** | На всеки **20 минути** по време на активни състезания. | Пази **18-те** най-нови (`BACKUP_DB_RETENTION_COUNT`) — около 6 часа история, която стига назад до предишното пълно резервно копие. | Управлява се от системата (`auto_db_YYYYMMDD_HHMMSS.tar.gz`). Не може да се изтрива ръчно през API (връща HTTP 403). |
| **Ръчно резервно копие** | Задейства се при поискване чрез бутона **„Създай резервно копие сега“**. | Пази се **за неограничено време**. Никога не се изтрива автоматично от процедурите за почистване. | Управлява се от администратор (`manual_YYYYMMDD_HHMMSS.tar.gz`). Може да се изтегля или изтрива през административния панел. |

Пълните резервни копия съдържат дъмп на PostgreSQL (`pg_dump`) и файловете от `uploads/` във файл `.tar.gz`; резервните копия само на базата данни съдържат единствено дъмпа. Ротираните файлове с журнали (`*.log.N`) се пропускат. Преди всяко резервно копие сървърът изисква свободно дисково пространство поне два пъти по-голямо от предишното резервно копие от същия вид и не по-малко от `MIN_BACKUP_DISK_GB`. Неуспешно автоматично резервно копие не се отчита като завършено и се прави нов опит при следващата 20-минутна проверка, като по всяко време в опашката или в изпълнение може да има най-много едно автоматично резервно копие.

## 10. Разпределяне и ограничаване на хардуерните ресурси на работните възли

По време на първоначалната настройка (`make setup-worker`) работните възли проверяват общия брой CPU ядра (`nproc`), RAM паметта (`/proc/meminfo`) и наличните GPU (`nvidia-smi`), като заделят 1 CPU ядро и 4 GB RAM за системни нужди.

### Формула за ограничаване на RAM паметта по време на изпълнение:
```text
budget_mb = (GPU_RAM_PER_TASK_GB if task.gpu_required else CPU_RAM_PER_TASK_GB) * 1024

if task_ram <= budget_mb:
    use task_ram as-is
elif task_ram <= budget_mb * RAM_CLAMP_FACTOR (1.05):
    clamp container memory to budget_mb (log warning)
else:
    reject task → Celery retry → dead-letter queue (/api/admin/dead-letters)
```

При сигнала `worker_ready` работните възли записват своята хардуерна спецификация в клиента за координация на Redis (`worker_spec:<hostname>`), а фонова нишка я опреснява на всеки `WORKER_HEARTBEAT_SECONDS` (по подразбиране 30) заедно с опашките, чийто консуматор е работният възел, и `last_seen`. Ключът изтича след един ден; работният възел се отчита като на линия, докато последният му сигнал за активност е на възраст под `WORKER_HEARTBEAT_STALE_SECONDS` (по подразбиране 90). Сигналите за активност захранват `GET /api/status` и `GET /api/admin/system-status` (раздел 11). Регистрацията на работните възли се управлява изцяло от сигнали — не съществува отделна задача за регистрация.

## 11. Крайни точки за състояние и проверка за изправност

| Крайна точка | Достъп | Предназначение |
| :--- | :--- | :--- |
| `GET /api/health` | Публичен | Работоспособност: база данни, кеш Redis, брокер Redis и диск. Връща 200 или 503 и се използва от проверките за изправност на контейнерите. Никога не проверява работните възли, така че липсващ работен възел не може да представи API като неработещо. |
| `GET /api/status` | Публичен | Обобщено състояние за външни проверки на достъпността, използващо стойностите на Statuspage `operational`, `degraded_performance`, `partial_outage` и `major_outage`. Кешира се за `STATUS_CACHE_SECONDS` (по подразбиране 30). |
| `GET /api/admin/system-status` | Администратор, жури | Подробните данни зад състоянието: опашки, работни възли и брой решения. Показва се в панела **Работни възли и опашки** на административния панел, който го запитва на всеки 15 секунди. |

И двете крайни точки за състояние се изчисляват от сигналите за активност на работните възли, дължините на опашките в брокера и базата данни. Уеб процесите никога не извикват Celery `inspect`.

| Компонент | Правило |
| :--- | :--- |
| `api` | `major_outage`, когато базата данни или брокерът Redis са недостъпни, в противен случай `operational`. |
| `scoring` | `major_outage`, когато нито един работен възел на линия не е консуматор на `cpu_queue`; `partial_outage`, когато друга опашка за оценяване има чакащи съобщения, но няма консуматор на линия; `degraded_performance`, когато най-старото решение в опашката е чакало по-дълго от `STATUS_QUEUE_DEGRADED_SECONDS` (по подразбиране 600); в противен случай `operational`. |

Общото `status` приема най-тежкото състояние сред компонентите. Работният възел се счита за на линия, когато последният му сигнал за активност е на възраст под `WORKER_HEARTBEAT_STALE_SECONDS` (по подразбиране 90); работните възли изпращат сигнал за активност на всеки `WORKER_HEARTBEAT_SECONDS` (по подразбиране 30).
